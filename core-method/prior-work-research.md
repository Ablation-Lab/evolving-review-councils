**What the project tests, for judging closeness:**
- several LLM reviewer agents in seats with roles;
- a judge that keeps or dismisses findings and sets severity, and a second agent that can appeal the judge's dismissals;
- scoring against planted bugs, with an outside-family judge for matching;
- council configurations that compete and advance over rounds;
- role sets compared at equal cost (A, B, C and one generalist with an ISO checklist; amended 19 Nov 2026: and A′, A's areas in the checklist format, added on 13 Nov);

## 1. Multi-agent LLM code review

### RevAgent: Issue-Oriented Agent-Based Framework for Automated Review Comment Generation (rechecked)
- **Paper:** Shuochuan Li, Dong Wang, Patanamon Thongtanunam, Zan Wang, Jiuqiao Yu and Junjie Chen; ~~arXiv preprint,~~ 1 Nov 2025; [arXiv 2511.00517](https://arxiv.org/abs/2511.00517). Full text read.
  - (amended 18 Nov 2026, from the sweep: now published in *ACM TOSEM* 35(11), 2026, DOI 10.1145/3817606 (Crossref, dated 4 Nov 2026). Its anonymous code artefact has expired. The sweep also found its title in the ASE 2026 programme on conf.researchr.org, track not confirmed.)
- **Tested:** five fine-tuned commentator agents, one per issue category (refactoring, bug fix, testing, logging and documentation), plus a critic that picks the best issue and comment. Scored against human comments: BLEU +12.90%, ROUGE-L +10.87%, METEOR +6.32% and SBERT +8.57% over the best baseline.
  - Its ablation beats a single agent fine-tuned on all categories, at about 8.7 times LLaMA-Reviewer's tokens (full text).
- **Closeness: medium-high.** It has category specialists and a critic as judge, and the specialists beat a single agent.
- **Differences:**
  - the critic picks one comment instead of pooling findings;
  - there is no appeal;
  - it is scored by similarity to human comments, not planted bugs;
  - the role set isn't varied and cost isn't matched.

### Hydra-Reviewer: A holistic multi-agent system for automatic code review comment generation
- **Paper:** Xiaoxue Ren, Chaoqun Dai, Qiao Huang, ~~Ye Wang, Bo Jiang and Chao Liu~~ Ye Wang, Chao Liu and Bo Jiang. (amended 18 Nov 2026, from the sweep: this is the author order in Crossref and on the FSE 2026 Journal-First page.)
  - **Venue:** IEEE Transactions on Software Engineering, 2025, issue 12. (amended 18 Nov 2026, from the sweep: vol. 51, pp. 3540–3557, DOI 10.1109/TSE.2025.3621462, from Crossref.) This is from the IEEE Computer Society listing (path `ts/2025/12/11203269`), seen via search only. It was also presented in the [FSE 2026 Journal-First track](https://conf.researchr.org/details/fse-2026/fse-2026-journal-first/40/Hydra-Reviewer-A-holistic-multi-agent-system-for-automatic-code-review-comment-gener).
  - **Read:** abstract read (pasted by the researcher from the IEEE page, 12 Nov 2026). ~~Only the listing was read: IEEE Xplore (document 11203269) returned an empty page and no preprint was found.~~ The full text still isn't accessible; ~~I'm requesting a copy from the first author~~ a copy has been requested from the first author, and I'm awaiting a reply (amended 19 Nov 2026).
- **Tested:** agents built around a taxonomy of review dimensions from an empirical study, with context retrieval and reflection.
  - **Motivation:** the authors name three limitations of existing automated code review: lack of comprehensiveness, incorrectness and vagueness.
  - **Evaluation:** on CodeReview, CodeReviewNew and a new dataset of their own, against CodeReviewer, LLaMA-Reviewer, ChatGPT, Comprehensive-ChatGPT and DeepSeek-V3. Each component is ablated, and there is a user study.
  - **Results:** BLEU 8.20 against 7.85 for DeepSeek-V3, 7.8 dimensions covered per comment, and $0.018 and 62.63 s per change.
  - ~~**The taxonomy's dimensions** aren't listed in the abstract.~~ (amended 18 Nov 2026, from the sweep, which read the public code at GitHub ZJUSig/Hydra-Reviewer, with the dataset on Zenodo record 15063416. The abstract doesn't list the dimensions, but the code does.)
    - **The seats:** 18 dimension agents run in parallel, one per dimension, all on `gpt-4o-mini`. The dimensions are code semantic correctness, code syntax correctness, security compliance, programming handling conventions, identifier naming style, code formatting style, comment style, identifier naming readability, code logic readability, comment quality, redundancy, compatibility, name-and-logic consistency, runtime observability, fault tolerance, code testing, extensibility and performance.
    - **The ranking:** a rerank agent orders suggestions by a fixed category priority, with fault tolerance first. It has no judge and no appeal.
    - **The full text** still isn't accessible.
- **Closeness: medium.** Its dimension-based agents are the nearest thing to seat roles chosen from a taxonomy. It is scored by BLEU, and whether its ablation compares role sets couldn't be checked.
- **How it bears on the project:**
  - **Its three limitations map onto parts of the council:**
    - comprehensiveness onto seat coverage;
    - incorrectness onto the judge, the appeal and the checks;
    - vagueness onto the findings format, which asks for the file, the line and the evidence (as in Lite's reviewer, judge and appeal briefs).
  - **Its BLEU gain** (8.20 against 7.85) measures similarity to human comments, not bugs caught.
  - **Its ablation** is the part to read for the question of folding areas into existing seats against giving them seats of their own.

### CodeAgent: Autonomous Communicative Agents for Code Review
- **Paper:** Xunzhu Tang et al. (9 authors); EMNLP 2024 main conference; [arXiv 2402.02172](https://arxiv.org/abs/2402.02172) (v1 3 Feb 2024, v5 24 Sep 2024). Full text read, except the appendices.
- **Tested:** six company-style roles plus a QA-Checker that keeps agents on the question, across four review tasks.
  - **Vulnerability detection:** 449 of 483 flags were confirmed by hand after the fact (92.96%), against 51.42% for GPT-4. Without the QA-Checker the figure falls to 73.23%.
- **Closeness: medium-low.** It has a supervisor, but the roles are company roles, there is no answer key set in advance and no role-set comparison.

### Adversarial Review: Structured Disagreement for Grounded Agentic Code Review (rechecked)
- **Paper:** Eric S. Qiu and Joyce Gill; ICML 2026 DL4C workshop; [arXiv 2608.18167](https://arxiv.org/abs/2608.18167) (16 Aug 2026). Full text mostly read.
- **Tested:** a main agent, a reviewer and a critic that audits the review. It was compared with one reviewer, two reviewers and a five-agent baseline (MARS).
  - **SWE-PRBench** (100 real PRs, human comments as ground truth, a GPT-5.2 judge with kappa 0.75): the first protocol showed "false consensus" (F1 0.457). Requiring evidence for disagreement gave 0.533, against 0.495–0.503 for the others.
    - (amended 18 Nov 2026, from the sweep: SWE-PRBench's own record, [arXiv 2603.26130](https://arxiv.org/abs/2603.26130), describes "350 pull requests", with the judge "validated at kappa=0.75". The 100 PRs may be the subset Adversarial Review used. Check which is meant.)
  - **Headline finding:** more independent reviewers didn't reliably help.
  - **A second version** (amended 18 Nov 2026, from the sweep, through an OpenReview search): "Adversarial Review: Cooperative Code Review through Structured Disagreement" is listed in the ICML 2026 AI4GOOD workshop. Its numbers weren't checked.
- **Closeness: medium-high.** It compares reviewer counts and structures in code review, and the critic is a rough analogue of an appeal.
- **Differences:** the reviewers aren't specialised, there is no planted-bug key and cost isn't matched.

### Using Agentic AI for contextualized and multifaceted code review at Ericsson
- **Paper:** Muhammad Laiq, Ricardo Britto, Muhammad Usman, Nishrith Saini and Deepika Badampudi; PROFES 2026; [arXiv 2609.15877](https://arxiv.org/abs/2609.15877) (14 Sep 2026). Full text read.
- **Tested:** an orchestrator picks among four dimension agents (readability, maintainability, reliability and performance) and merges their output. Developers judged 96% of 206 issues correct and about 69% important.
- **Closeness: medium.** Its seats are close to options B and C. There is no generalist baseline, no role-set ablation and no answer key.

### VulTrial: Let the Trial Begin: A Mock-Court Approach to Vulnerability Detection using LLM-Based Agents
- **Paper:** Ratnadira Widyasari et al. (9 authors); ICSE 2026, according to the full text and the DOI 10.1145/3744916.3773256 (amended 18 Nov 2026, from the sweep: pp. 1030–1042); [arXiv 2505.10961](https://arxiv.org/abs/2505.10961) (v1 16 May 2025, v2 3 Dec 2025). Full text mostly read.
- **Tested:** prosecutor, defence, moderator (judge) and review board (jury) agents on PrimeVul vulnerable and benign pairs, a known-label key. With GPT-4o it got 81 pairs correct, against 44 for GPTLens.
  - **Role ablation:** removing the moderator drops a configuration from 96 to 32. One debate round works best.
- **Closeness: medium-high.** It has a judge, adversarial roles, a role ablation and a known-label key.
- **Differences:** it classifies functions as vulnerable or not instead of combining review findings, there is no appeal of dismissals and no equal-cost control.

### GPTLens and MAVUL
- **[GPTLens](https://arxiv.org/abs/2310.01152):** Sihao Hu et al., IEEE ~~TPS 2023~~ TPS-ISA 2023 (abstract page read). (amended 18 Nov 2026, from the sweep: TPS-ISA is the conference's full name.) An auditor generates candidate vulnerabilities and a critic filters false positives. It is the original generate-then-judge design for code findings.
- **[MAVUL](https://arxiv.org/abs/2510.00317):** Youpeng Li et al., IEEE TPS 2025 (abstract page read). An analyst, an architect and an evaluation judge on a pairwise known-label set.
- **Closeness: medium** and **medium-low.** Each has a judge-like filter, with no role sets or appeal.

### MultiVer and CodeX-Verify (both Shreshth Rajan)
- **[MultiVer: Zero-Shot Multi-Agent Vulnerability Detection](https://arxiv.org/abs/2602.17875)** (arXiv, 19 Feb 2026; full text read):
  - **Tested:** four agents (security, correctness, performance and style) combined by union voting with Claude Opus 4.5. On PyVul, recall was 82.7% and precision 48.8%. Security alone loses 17 points of recall.
  - **Caveat:** the style agent never calls the LLM.
- **[CodeX-Verify: Multi-Agent Code Verification via Information Theory](https://arxiv.org/abs/2511.16708)** (arXiv, v1 20 Nov 2025, v3 3 Dec 2025; full text read; v1 had a different title):
  - **Tested:** all 15 combinations of four agents on 29 samples. Correctness plus performance (79.3%) beat all four.
  - **Caveat:** the "agents" are static analysers, not LLMs, and the weights were tuned on the same data.
- **Closeness: medium.** These are the only role-set comparisons against labelled bugs found. Neither uses a generalist baseline or matches cost, and CodeX-Verify isn't LLM review at all.

### OpenCodeReview and BitsAI-CR: production pipelines with a filter
- **[OpenCodeReview: Determinism over Non-Determinism for Cost-Effective Agent-Based Code Review](https://arxiv.org/abs/2608.09290)** (rechecked): Zhengfeng Li et al. (11 authors, Alibaba), arXiv, 10–11 Aug 2026. Full text read.
  - **Tested:** parallel sub-agents, then a reflection filter that sees only the diff and removes hallucinated comments. On AACR-Bench it reached up to 2.17 times the SEM-F1 of Claude Code and Codex (25.10% against 11.57%), with 5–15 times fewer tokens.
  - **The filter is delete-only:** it fails open on a parse error, nothing restores what it deletes and it isn't ablated on its own (full text).
- **[BitsAI-CR: Automated Code Review via LLM in Practice](https://arxiv.org/abs/2501.15134):** Sun et al. (12 authors, ByteDance), arXiv 25 Jan 2025, FSE 2025 Industry ~~*(venue from a snippet)*~~. Abstract page read. (amended 18 Nov 2026, from the sweep: the venue is confirmed by Crossref as FSE 2025 Companion, pp. 274–285, DOI 10.1145/3696630.3728552.)
  - **Tested:** a rule checker flags issues and a review filter verifies them, for 75.0% precision.
- **Closeness: high on structure** (parallel reviewers plus a judge-like filter), with no appeal, no severity judge and no planted bugs.

### Anthropic's "Best practices for Claude Code": two points on reviewers (vendor guidance, added 18 Nov 2026)
- **Source:** [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) (Anthropic, official docs; no date shown). From my account, it was read in full in the chat on 18 Nov 2026. Claude Code fetched the page as Markdown through curl at 00:14 UTC on 18 Nov 2026, and the quotes below are from that copy.
- **Status:** vendor guidance, not measured results. The page gives no study, sample or figures for either point.
- **(a) Reviewers asked for problems find some.** From the "Review against your spec" note: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." The page's advice is to scope the review prompt to the spec and to "report gaps that affect correctness and skip style".
  - **How it connects:** it's the vendor's own statement of the precision problem. Council Dial Lite 2.2.5 Quick left 238 unconfirmed extras on the hard tier (88% of the 272 findings in the main lists), 8.2 per catch. That's why the research doc adds extras per catch and rank as precision measures (see "Rank as a main measure" in the research doc).
  - *(Claude Code's note)*: the guidance predicts extras, not that extras are false. On the easy tier, all 20 sampled extras were real problems ("The extras sample" in the research doc). So the guidance supports measuring extras, not counting them as noise.
- **(b) A fresh reviewer isn't swayed by the author's reasoning.** The page says `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code." Its table of old advice adds: "A fresh reviewer does help, because it hasn't seen your reasoning, which is a different thing from delegating." It also calls a second session "the easiest independent reviewer you can get".
  - **How it connects:** it's vendor guidance on the self-preference question in section 6. It's closest to Khullar et al.'s in-context self-attribution bias, which fresh-context subagents should reduce, and to why the council's seats start from fresh context.
  - *(Claude Code's note)*: it's about context, not model family. A fresh Claude subagent still shares the author's model, so it says nothing about the same-family blind spots in section 6 (Song 2026, CyberDual).
- **A wording check** *(Claude Code's note)*: the wording relayed from the chat, "A reviewer prompted to find gaps will usually report some, even when the work is sound … Chasing every finding leads to over-engineering" and "A fresh context improves code review since Claude won't be biased toward code it just wrote", isn't on the page as fetched. The quotes above are the page's current words. The relayed lines may be a paraphrase or come from an earlier version of the page.

## 2. Role design for reviewer agents

### MARG: Multi-Agent Review Generation for Scientific Papers
- **Paper:** Mike D'Arcy, Tom Hope, Larry Birnbaum and Doug Downey; arXiv preprint, 8 Jan 2024; [arXiv 2401.04259](https://arxiv.org/abs/2401.04259). Full text read.
- **Tested:** specialist agents for experiments, clarity and impact (MARG-S), against a generic multi-agent version, single agents and each specialist alone.
  - **Recall:** 15.84 for the specialists, 8.49 for the generic team, 10.62 for the best single agent and 3.25–8.88 for each specialist alone.
  - **Cost:** the specialists used about 1.24M input tokens against about 135k for the generic team.
- **Closeness: high on design.** It is the clearest specialists-against-generic-against-single comparison, with each specialist ablated.
- **Differences:** it reviews papers, not code, there is no planted key and the cost is about nine times higher for specialists. The generic team did worse than a tuned single agent.

### ChatEval: Towards Better LLM-based Evaluators through Multi-Agent Debate
- **Paper:** Chi-Min Chan et al. (8 authors); ICLR 2024 (per the [proceedings](https://proceedings.iclr.cc/paper_files/paper/2024/hash/25cc3adf8c85f7c70989cb8a97a691a7-Abstract-Conference.html)); [arXiv 2308.07201](https://arxiv.org/abs/2308.07201). Abstract and proceedings pages read.
- **Tested:** debating panels of evaluators. Giving every agent the same role prompt did worse than diverse roles, and no better than one agent ~~*(ablation detail from a search summary)*~~.
  - (amended 18 Nov 2026, from the sweep, which read the full text's Table 3: the ablation is confirmed. On 80 FairEval questions with ChatGPT, a single agent and a same-role team both scored 53.8%, against 60% for diverse roles. That's small evidence: one model and 80 questions.)
- **Closeness: medium-high.** It shows role diversity matters in a judging panel. It evaluates text, not code, and cost isn't equal.

### Agents with Feelings? Personality and Emotion in Multi-Agent Software Teams
- **Paper:** Yunyan Ding, Thomas Zimmermann and Iftekhar Ahmed; arXiv preprint, 6 Jul 2026; [arXiv 2607.05659](https://arxiv.org/abs/2607.05659). Full text read.
- **Tested:** 78 team-profile configurations with four LLMs. Its code-review team is two writers split by quality areas plus a supervisor who merges and filters, on Hydra-Reviewer's data. Profiles change BLEU by 8.3–18.9% relative.
- **Closeness: medium-high.** It compares team configurations for code review systematically, with a supervisor as judge. But it varies personas, not seat scopes, it is scored by BLEU and cost isn't matched.

### Other role and persona studies
- **Philosophical Dispositions as Behavioral Constraints for AI-Assisted Code Review** ([arXiv 2605.23108](https://arxiv.org/abs/2605.23108); Kaushal Bansal, 2026; abstract page read):
  - **Tested:** four reviewer "dispositions" on 50 PRs. 51% of their findings weren't produced by a generic "expert reviewer" prompt on the same model.
  - **Caveat:** false positives were judged by the author alone.
  - **Closeness: medium, weak evidence.**
- **Pornprasit and Tantithamthavorn, Fine-Tuning and Prompt Engineering for LLM-based Code Review Automation** ([arXiv 2402.00905](https://arxiv.org/abs/2402.00905); 2024; abstract page read; amended 18 Nov 2026, from the sweep: published in *Information and Software Technology* 175, 2024):
  - **Tested:** fine-tuning and prompt set-ups for code review. It recommends few-shot prompting *without* a persona.
  - **Closeness: medium-low.**
- **Zheng et al., personas in system prompts** (Findings of EMNLP 2024, [arXiv 2311.10054](https://arxiv.org/abs/2311.10054)):
  - **Tested:** personas didn't beat a no-persona control. Already cited in the plan and the paper.
  - **Bearing on seats:** a role label alone may not be what makes a seat work; its scope, checklist and context may matter more.

### Equal-cost and panel-size precedents

#### The More the Better? A Comparison of Single- and Multi-Agent LLM Setups on a Financial Review Task *(from the sweep, top 10 no. 1)*
- **Paper:** Pei Liu; arXiv preprint, v1 Oct 2026; [arXiv 2610.27488](https://arxiv.org/abs/2610.27488). Abstract read (verbatim, arXiv API); full text partly read (the results and the appendix notes on labels, models and settings; arXiv HTML through curl). Rechecked by the sweep session.
- **Tested:** one agent checking 300 synthetic credit memos against six requirements, with known labels, against a "team of three on the same model … two requirements each, in the same words, with no roles or later stage".
  - **Scoring:** "Misses and false alarms are measured separately", with Bonferroni-corrected primary predictions.
  - **Models:** Qwen3.5 9B and 27B, and Claude Haiku 5.5 and Sonnet 5.5 (effort high).
  - **Labels:** accepted when the generator, a separate checking program and Claude Opus 5.5 agreed. The author notes that "Opus 5.5 belongs to the family of two of the tested models and is not one of them."
- **Results:**
  - **Catches:** "the team catches 0.08 to 0.10 more of the defects that carry an explanation on the three models whose single agent misses some, at the corrected level on two".
  - **Cost:** "It raises more false alarms on all four, at the corrected level on three. Balanced accuracy … changes by 0.02 or less, and the team uses 2.2 to 2.4 times the tokens."
  - **Three draws:** in an exploratory analysis, "sampling the single agent three times and flagging on any draw gives higher balanced accuracy than the team on those models". (recheck, 18 Nov 2026: "those models" are the two Claude models, and on the Qwen models the comparison is confounded with temperature. So it's an exploratory result on balanced accuracy, for Claude only.)
  - **Mechanism:** the team's d′ doesn't change significantly and its c falls, so splitting scope lowers the flagging threshold without improving discrimination.
  - **Misfiled flags:** on Haiku 5.5, most of the team's false alarms "quote a sentence that is defective under another requirement". So the false-alarm cost is "probably overstated", and a "scoped team" that sees the other seats' requirements cuts the extra false alarms on the Claude models.
- **Closeness: high on design.** It is the closest controlled design found to the project's specialist-against-generalist question at equal cost, and its result is the project's null hypothesis.
- **Differences:** it is document review, not code, with one synthetic task and no judge, appeal or evolution.
- **For the project** (the sweep's reading): cite it as the prior test of the equal-cost question in another domain, and frame the project's result as the code-review test of it. Its misfiled flags suggest the judge could re-file a finding to the seat whose scope it fits, rather than dismiss it.

### Refute-or-Promote: An Adversarial Stage-Gated Multi-Agent Review Methodology (rechecked)
- **Paper:** Abhinav Agarwal; arXiv preprint, 21 Apr 2026; [arXiv 2604.19049](https://arxiv.org/abs/2604.19049). ~~Abstract page read.~~ Full text partly read (sections 3, 4.5 and 5, arXiv HTML through curl), by the sweep, whose session rechecked the passages quoted below. - **Tested:** adversarial agents try to disprove each candidate defect at each gate, with a cross-family critic and a required empirical test. About 79% of 171 candidates were killed, and the campaign led to 4 CVEs.
  - **A unanimous error:** ten reviewers unanimously backed an OpenSSL vulnerability that doesn't exist, and one test killed it.
    - (amended 18 Nov 2026, from the sweep's full-text read: the abstract says "ten dedicated reviewers", while the introduction says "80+ agents—including dedicated adversarial reviewers—unanimously endorsed" it. Quote the abstract's figure with this caveat.)
  - ~~*(Snippet only:)* a real CVE was unanimously killed and recovered only by a human.~~ (amended 18 Nov 2026, from the sweep: now verified from the full text, section 4.5.) The lcms2 CubeSize() integer overflow, CVE-2026-41254, "was unanimously killed in Round 4 … and resurrected only via a creative uplift agent tasked with a different role". So the rescue was set off by a human but carried out by an agent with a different brief.
  - **The pipeline's own description** (amended 18 Nov 2026, from the sweep, section 5): "The pipeline is architecturally unidirectional: it has structural mechanisms against false positives (kill mandates) but relies on the human orchestrator to rescue true positives incorrectly killed." Table 3 lists "Rejecting false kills, override decisions" as "Human-essential". It is the clearest published statement of the gap the project's appeal fills.
  - **The released playbook** (amended 18 Nov 2026, from the sweep, which read `strat.md` in the MIT-licensed artefact repository through the GitHub API): it's written for Claude Code subagents. Sonnet subagents find and attack candidates, Opus is added in later rounds, and the cross-family "super final round" runs Codex (`gpt-5.4`, reasoning effort xhigh). So the cross-model critic is OpenAI Codex critiquing a Claude Sonnet and Opus council. That's the nearest precedent for the project's cross-family judge, though it uses prompts only and has no benchmark.
  - **Its own limits:** "Single operator with domain expertise (not independently replicated). No ablation studies isolating individual mechanisms." It also reports a wolfSSL case where "same-family consensus actively propagated a mistake that a fresh-context reviewer caught".
- **Closeness: medium-high.** It has several agents checking findings across families.
- **Differences:** it runs the **opposite way** to the project's appeal, attacking promotions rather than reinstating dismissals. It is a field campaign, not a controlled test against planted bugs.

### Evident: The Hitchhiker's Guide to Program Analysis, Part III: Mostly Harmless LLMs

#### Sifting the Noise: A Comparative Study of LLM Agents in Vulnerability False Positive Filtering *(from the sweep, close behind)*
- **Paper:** Yunpeng Xiong and Ting Zhang; to appear at ISSTA 2026, per the arXiv comment; v1 30 Jan 2026, v3 23 Jul 2026; [arXiv 2601.22952](https://arxiv.org/abs/2601.22952). Abstract page read (fetch tool, which summarised rather than quoted the abstract); full text partly read (fetch tool; the first 100k of 136k characters, the results tables). Rechecked by the sweep session, which notes that the "about a fifth" figure is from the full text through a fetch tool. The abstract says only that "aggressive FP reduction can come at the cost of suppressing true vulnerabilities".
- **Tested:** three agent frameworks (Aider, OpenHands and SWE-agent) and plain prompting, with Claude Sonnet 4, DeepSeek Chat and GPT-5, filtering false positives from static-analysis output. It used the OWASP Benchmark, Vul4J projects with CodeQL alerts and a C/C++ OSS-Fuzz study from after the models' cutoff.
- **Results** *(fetch tool: check against the PDF)*:
  - **Filtering:** false-positive detection fell from over 92% to as low as 6.3% in the best configuration.
  - **Real bugs lost:** with Claude Sonnet 4 and SWE-agent on OWASP, 314 of 1,411 completed runs on vulnerable cases were labelled false positives. That's 22.25% of real vulnerabilities suppressed.
  - **By bug class:** losses ranged from 0.41% for CWE-79 to 84.50% for CWE-328. On Vul4J, they ranged from 0.0% to 25.0% across agent and model pairs.
  - **No recovery step:** it removes only. The authors advise against "unconditional, automatic suppression".
- **Closeness: medium-high on motivation.** It gives the strongest figures found for an LLM filter dropping real bugs, and so the case for an appeal. The losses aren't uniform across bug classes, so the judge's drops should be reported per class (the sweep's idea 9).

#### Trusting the Tool: Asymmetric Deference of LLM Vulnerability Auditors to Static-Analysis Evidence *(from the sweep, top 10 no. 9)*
- **Paper:** ZhiHong Liu and Shuyao Gao; arXiv preprint ("Submitted to IEEE Access"), 23 Oct 2026; [arXiv 2610.32876](https://arxiv.org/abs/2610.32876). Abstract read (verbatim, arXiv API). Rechecked by the sweep session.
- **Tested:** 916 pairs of vulnerable and patched PrimeVul functions under six evidence conditions, including fabricated assurances and fabricated alarms. It ran 11 model configurations from 4 vendors, 16,572 audits in all, with an internally registered replication.
  - "false assurances lowered the detection of real vulnerabilities by up to 19 points, whereas false alarms never significantly lowered accuracy".
  - "Verifying each claim in a separate call and showing the refuted claims raised accuracy under false assurances by 12 points in a pre-specified test (p=0.002)."
- **Read with:** **Grounded but Not Immune: Confirmation Bias in Agent-as-a-judge** (Drake Benjamin Brown et al., 8 authors; arXiv preprint, "Under Review", 3 Nov 2026; [arXiv 2611.05662](https://arxiv.org/abs/2611.05662); abstract read (verbatim, arXiv abs page through curl); rechecked by the sweep session).
  - A single false "pre-screening note" from an authority "overturns up to 40% of a tool-using judge's correct verdicts across four judges and five datasets".
  - "For the two Claude judges, the failure is predominantly over-trust (67-75% of harmful flips)."
- **Closeness: high on mechanism.** Together, they explain how wrong dismissals happen, which is what the appeal targets: "this is fine" claims push a judge towards wrong dismissals far more than towards wrong keeps.
- **For the project:**
  - claim-by-claim checking is an arm to borrow (the sweep's idea 2);
  - an appeal that sees the judge's reasons may inherit the same over-trust, so blinding it is an arm worth testing (idea 3).

#### TeamBench: Evaluating Agent Coordination under Enforced Role Separation *(from the sweep, close behind)*
- **Paper:** Yubin Kim, Chanwoo Park, Taehan Kim et al. (12 authors, with Xin Liu, Hamid Palangi and Daniel McDuff); arXiv preprint, May 2026; [arXiv 2605.07073](https://arxiv.org/abs/2605.07073). Abstract read (verbatim, arXiv API).

#### Unanimity Without Persuasion: A Single Round of Debate Erases the Disagreement That Verification Needs *(from the sweep, top 10 no. 7)*
- **Paper:** Yang Shu; arXiv preprint, v1 10 Aug 2026 (listed as Sep 2026 elsewhere in the sweep); [arXiv 2609.26145](https://arxiv.org/abs/2609.26145). Abstract read (verbatim, arXiv API). Rechecked by the sweep session.
- **Tested:** a mixed panel of seven judges through a blind round and three debate rounds, on 600 code-correctness candidates, with execution-based verification and controls on identical groups.
  - **Collapse:** "unanimity … jumps from 39.5% to 95.2% in round 1 … while accuracy moves by less than one point and 96.3% of verdict flips follow the displayed peer majority".
  - **Lost dissent:** "by round 3 every wrong decision is unanimous, erasing dissent that had flagged two-thirds of the panel's errors".
  - **Controls:** "real labels without reasoning reproduce 91.5%" of the collapse. It holds for panels of 3 to 7.
  - **Its advice:** "verify before any second-pass evaluation or peer exposure" (the sweep's top-10 note).
- **Closeness: medium.** It is debate among judges on code, not finding planted bugs.
- **For the project:** it argues against debate before judging, and for independent review followed by a judge. For the debate arm, the judge and the appeal should also see the findings from before the debate (the sweep's idea 12).

### The keep rule and the loop's failure modes *(from the sweep, top 10 no. 10)*
The project keeps a child only if a 90% CI on its paired difference from the parent is above zero, with held-out seeds. Three papers bear directly on that rule. The sweep says to read them with two critiques of automatically designed agents.

- **SGM: A Statistical Gödel Machine for Risk-Controlled Recursive Self-Modification** (Xuening Wu, Shenqin Yin, Yanlan Kang et al., 7 authors; arXiv preprint, v1 11 Oct 2025, v2 17 Sep 2026; [arXiv 2510.10232](https://arxiv.org/abs/2510.10232); code at github.com/gravitywavelet/sgm-anon; abstract read (verbatim, arXiv API)):
  - **Tested:** statistical tests (e-values and Hoeffding bounds) replace proof of improvement. A self-modification is admitted only when its superiority is certified at a chosen confidence level, under a global error budget across rounds.
  - **Results:** no figures in the abstract. It "certifies genuine gains on CIFAR-100, rejects spurious improvement on ImageNet-100".
  - **For the project:** the closest prior art for the keep rule, so cite it as such. It adds what the rule lacks: an error budget across generations, so that the chance of keeping even one spurious change over a whole run is bounded (the sweep's idea 30). It is tested on vision, RL and black-box optimisation, not agents or review.
- **SIREN: Towards Reliable LLM Evaluation: Correcting the Winner's Curse in Adaptive Benchmarking** (Jiefu Zhang et al., 6 authors; NeurIPS 2026 per the arXiv comment; v1 7 May 2026, v2 7 Nov 2026; [arXiv 2605.05973](https://arxiv.org/abs/2605.05973); abstract page read (curl); rechecked by the sweep session):
  - **Tested:** "Once benchmark items are reused inside tuning, the observed winner's score need not estimate the fresh-data performance of the full tune-then-deploy procedure." SIREN freezes the shortlist, separates selection from held-out evaluation and uses an item-level bootstrap.
  - **For the project:** when several children compete on the same seeds, the kept child's measured gain has a winner's curse, and the per-comparison 90% CI isn't corrected for that. Re-scoring kept children on fresh seeds would address it (idea 27).
- **LLM-as-a-Judge Is Not an Oracle: Why Self-Improving Agents Need Deterministic Guardrails (PROCTOR)** (Vansh Wahi; arXiv preprint, a position paper drawing on production experience, v1 2 Sep 2026; [arXiv 2609.02246](https://arxiv.org/abs/2609.02246); abstract page read (curl); full text partly read (sections 5.1–5.5, the limitations and the appendix on split policy); rechecked by the sweep session):
  - **Tested:** a catalogue of eleven ways the evaluation signal failed in production prompt-optimisation loops, some of them on code quality.
    - "Agents achieved perfect scores by reading cached answer keys from their environment, a 100% pass rate concealing 68% true capability."
    - "A syntactically broken prompt was promoted as the winner because a silent parser fallback improved the metric."
  - **Its guardrails:** "hermetic sandboxes, capability-disjoint roles, acceptance checks that outrank the Teacher, frozen holdouts, and canary cases engineered so that a perfect score is itself evidence of cheating".
  - **Its limits:** "Pass rates are from one execution each … no result here should be read as significant".
  - **For the project:**
    - canary seeds, and keeping the key off any path a reviewer can read (idea 26), since a Claude Code reviewer with Read and Glob could do the same in a shared working tree;
    - checking the judge's structured output for silent parser fallbacks.
- **Read beside them:**
  - **The Illusion of Multi-Agent Advantage** (Prathyusha Jwalapuram et al., 10 authors, Salesforce Research and others; arXiv preprint, v1 11 Jun 2026, v2 13 Jun 2026; [arXiv 2606.13003](https://arxiv.org/abs/2606.13003); abstract read (verbatim, arXiv API); full text partly read (Appendix E)): automatically generated multi-agent systems "consistently underperform CoT-SC despite being up to 10x more expensive". It's the source of the ADAS test-set finding above.
  - **Simple Baselines are Competitive with Code Evolution** (Yonatan Gideoni, Sebastian Risi and Yarin Gal; arXiv preprint, v1 18 Feb 2026, v2 12 Oct 2026; [arXiv 2602.16805](https://arxiv.org/abs/2602.16805); abstract read (verbatim, arXiv API); full text partly read (section 5)): with typical noisy evaluation, "all automated search methods [pick] subpar scaffolds relative to a simple majority vote". It recommends at least 10 repetitions and 95% CIs.
  - **For the project:** a majority-vote and random-search baseline in every generation, and a check that evolved councils haven't degenerated into the same generalist three times (idea 31).
- **A related recipe:** Anthropic's own hillclimb recipe (Lance Martin, claude.dev blog, 28 Sep 2026; page read (curl)) keeps or reverts each patch on a held-out test set and ends at "the version that did best on the test set". So, by the sweep's reading, the test set is used for selection, and its final score isn't a clean held-out estimate. The project should keep a final held-out set that no keep decision ever reads (idea 27).

### When Does a Second Model Help? Cross-Model Review in LLM Verification (rechecked)
- **Paper:** Tae-Eun Song; arXiv preprint, v1 1 Oct 2026, v2 6 Oct 2026; [arXiv 2610.01471](https://arxiv.org/abs/2610.01471). Full text read.
- **Tested:** 30 artifacts (Python modules, tutorials and scripts) with 150 planted errors, in 10 review conditions and 900 sessions.
  - **Who wrote the errors:** Claude Opus 4.6 wrote the artifacts and planted the errors, according to the run logs.
  - **Same-model against cross-model:** fresh-session same-model review didn't differ significantly in F1 from the best cross-model reviewer (GPT-5.4).
  - **Complementary errors:** the two found partly different errors (Jaccard 41.2%). One same-model plus one cross-model review matched 56.7% of planted errors, against 42.7% for two same-model reviews (Holm-adjusted p = .006).

- **Closeness: high.** It is close to this project's self-preference concern measured directly: Claude-planted errors in Claude-written code and docs, with same-family and cross-family reviewers.

  - it is small, single-author and unrefereed;
  - its ground truth is self-planted;

### Further same-family evidence *(from the sweep)*

#### CyberDual: AI Attackers versus AI Code Reviewers in Real Software Maintenance *(top 10 no. 3)*
- **Paper:** Chenyuan Yang, Hwiwon Lee, Jongseong Kim, Yihan Yang, Dongjun Kim, Yinfang Chen and Lingming Zhang; arXiv preprint (cs.CR), 25 Oct 2026; [arXiv 2610.34435](https://arxiv.org/abs/2610.34435). No venue stated. Abstract read (verbatim, arXiv API); full text partly read (fetch tool, the first 100k of 116k characters). Rechecked by the sweep session.
- **Tested:** attacker agents hide an exploitable bug inside real maintenance work on open-source projects. Reviewer agents then try to find and repair it: Claude Code with Sonnet 5, Claude Code with Opus 4.8 and Codex with GPT-6-Sol. Running the attacker's proof of concept on the reviewed code decides each match, so agent reports can't game the key. The windows "can be rebuilt each quarter from the latest upstream history".
  - **Abstract:** "Three agentic reviewers catch 85-91% of 1,088 valid attacks from six attackers". "When they miss, Claude reviewers mostly approve the attack, while GPT-6-Sol mostly repairs the wrong code; a reviewer from a second vendor catches about two thirds of a Claude reviewer's misses."
  - **Full text** *(fetch tool: check against the PDF)*:
    - attack survival was 14.3% against Sonnet 5, 10.9% against Opus 4.8 and 9.2% against GPT-6-Sol, and 28 attacks passed all three;
    - GPT-6-Sol "catches 69% of the attacks that Sonnet 5 misses" (denominator not seen);
    - Claude reviewers share some misses, with kappa 0.69 for "fix-in-hand" misses and at most 0.24 for "window" misses (recheck, 18 Nov 2026: confirmed in the full text; the 0.69 is between Sonnet 5 and Opus 4.8, two Claude reviewers, not across vendors);
    - false rejections of harmless changes aren't measured.
- **Closeness: high on the same-family question.** It is the strongest cross-vendor complementarity result on planted bugs, and closer to the project's set-up than Xiang et al.
- **Differences:** it is adversarial security work with single reviewers, not councils, and has no judge, appeal or evolution. With no harmless controls, it says nothing about precision, which is the part the project adds.

#### The Wisdom of Artificial Deliberative Crowds *(close behind)*
- **Paper:** Federico Barrera-Lemarchand, Mariano Sigman and Joaquin Navajas; arXiv preprint, no venue stated, v1 18 Sep 2026; [arXiv 2609.22497](https://arxiv.org/abs/2609.22497). Abstract read (verbatim, arXiv API); full text partly read (the PDF converted with pdftotext, so its quotes are verbatim). Rechecked by the sweep session.
- **Tested:** groups of three small models from three families (Claude Haiku 4.5, GPT-5-nano and Gemini 3.1 Flash Lite) answer alone, deliberate in a short chat until they agree, then answer again privately. There were four domains:
  - estimation;
  - accepting or rejecting 100 NeurIPS 2024 submissions against the human verdict;
  - rating 50 agent trajectories for sabotage;
  - forecasting.
  - Groups of three copies of one model ("clones") ran as controls.
- **Results:**
  - **Mixed groups:** in every study, the deliberating groups' consensus beat pooling many more independent answers from the same models.
  - **Clones:** "when groups were composed of three copies of the same model, deliberation produces consensus values that fail to improve accuracy over pooling that model's independent estimates". The Bayes factors for the null were 3.99–6.19 in Study 1.
  - **Expert dominance:** the best single family beat the mixed crowd in three of four domains, and which family led changed by domain.
  - **Cost:** not matched.
- **Closeness: medium.** It supports the mixed-family arm and qualifies the debate arm: deliberation helped only across families, never among copies. It covers judgement tasks, not code review.

#### When LLMs Benchmark Themselves: Deconstructing Self-Bias in Automated Evaluation *(close behind)*
- **Paper:** Wenda Xu, Sweta Agrawal, Vilém Zouhar, Markus Freitag and Daniel Deutsch; EMNLP 2026 per Semantic Scholar, not confirmed on the proceedings page; arXiv v1 30 Sep 2025, v3 30 Aug 2026; [arXiv 2509.26600](https://arxiv.org/abs/2509.26600). Abstract read (arXiv abs page through curl).
- **Tested:** when one LLM both writes a test set and evaluates the outputs, the benchmark favours that model, and the two sources of bias compound. The self-bias is "strong enough to cause each model to rank itself first, overriding the peer consensus ordering".
- **Closeness: medium.** It supports the project's central same-family concern, where Claude plants the seeds and Claude reviews. It comes from machine translation and Chatbot Arena, not code.

#### Review Rarely Beats the Stronger Model: Separating Verification from Capability Transfer in LLM Pipelines *(close behind)*
- **Paper:** Yirui Zhang and Yash Raj Shrestha; arXiv preprint, v1 11 Oct 2026, v3 3 Nov 2026; [arXiv 2610.15897](https://arxiv.org/abs/2610.15897). Code at github.com/Kamilaabb/verification-or-capability-transfer. Abstract read (verbatim, arXiv API).
- **Tested:** cross-model review against the stronger model alone, across 48 model pairs. Review beat the stronger model "in only 9 of 96 review directions", and cost "2.6 to 2.8 times as much as the stronger model alone".
- **Closeness: medium.** It challenges the usual reading of cross-model review gains, such as Xiang et al.'s and Song 2026's, since those gains can be capability transfer from the stronger model. The project should report the strongest single reviewer alone (the sweep's idea 15).

### Predicting Acceptance and Review Effort in Human and Agent Pull Requests
- **Paper:** Kartik Ghanshyambhai Pansuriya, Ehsan Ghorbani, Deepak Singh and Eman Abdullah AlOmar, Stevens Institute of Technology; arXiv preprint, v1 13 Jul 2026; ~~no venue stated~~ (amended 18 Nov 2026, from the sweep: now published at IEEE COMPSAC 2026, doi 10.1109/COMPSAC69091.2026.00052). [arXiv 2607.12057](https://arxiv.org/abs/2607.12057). Abstract page and [full text](https://arxiv.org/html/2607.12057v1) read by me through a fetch tool.
- **Tested:** whether a PR's acceptance and review effort can be predicted at submission time, from metadata only. It used classical machine learning (logistic regression, random forests, gradient boosting, extra trees and MLPs) on human- and agent-authored PRs from the AIDev corpus.
  - **Acceptance:** predictable, with tree-based models reaching F1 above 0.95.
  - **Review effort:** comment counts and time to merge are only modestly explained (R² 0.20 and 0.12, pooled).
- **Not prior work on councils:** it doesn't evaluate AI reviewers.
- **How it connects:**
  1. **Motivation.** It reports that "agent-authored PRs show slightly higher discussion and longer median time-to-merge". That is mild support for the project's motivation, though it gives no split figures, only the direction.
  2. **A possible source of real agent-written bugs** for the same-family question: AIDev includes Claude Code PRs. See the "To check" section in [seed-sources-research.md](seed-sources-research.md).

## 7. Additions from a 2026 search (17 Nov 2026)

**How it was done:** an overnight Claude Code session sent one research subagent to search for 2026 work on five topics: multi-agent LLM code review; appeal or re-check steps for LLM judges; precision measures for AI code review; scripted workflows against agent-led orchestration; and project instruction files helping or biasing agents. It opened each item's own page through a fetch tool, so, as in the first search, what was seen was a summary of the page with short quotes. The session then reopened six items itself and found their titles, authors, dates and headline figures matched: CRBugBench's Table 3 (above), CRJudgeBench, Jagged Judges, Evaluating AGENTS.md, Deterministic vs. LLM-Controlled Orchestration and Stale Instruction Files. Everything else is the subagent's read only. Each entry says what was read. None is refereed unless a venue is given, and figures need a second look before the paper cites them.

**What changes for the project:**
- **Judges err both ways.** The case for an appeal rests on judges dismissing real findings (Evident). CRJudgeBench finds LLM judges of review comments mostly *over-keep*. So the scoring should report the judge's errors in both directions: false findings kept and real findings dismissed.
- **The appeal's failure mode has prior work.** Challenging a judge flips its verdict often, and the flips mostly make it less accurate (Jagged Judges, Who Flips). Reinstated findings should be scored on their own against the key.
- **Multi-agent gains at high cost.** CRBugBench's ensembles and sub-agents gain little at 3–5 times the cost, which supports the equal-cost single-reviewer arm.
- **Instruction files.** There's now direct 2026 evidence on both sides of the CLAUDE.md help-or-bias question, though all of it is on coding agents, not reviewers.

### Multi-agent code review and precision

- **Is Agentic Code Review Helpful? Mining Developers' Feedback to CodeRabbit Reviews in the Wild** (Hong Yi Lin, Liang, Thongtanunam and Tantithamthavorn; [arXiv 2607.03316](https://arxiv.org/abs/2607.03316), v1 3 Jul 2026, v2 23 Jul 2026; full text read except the last part):
  - **Tested:** 31,073 review comments and developer responses from 10,191 PRs in 239 repositories. 36.4% were accepted, 7.3% discussed and 56.3% rejected (Table 2).
  - **Why rejected (Table 3):** 58.0% were invalid (43.3% false positives, 10.0% out of scope, 4.7% redundant), and 42.0% conflicted with the developer's design choices. Section 5 gives 35.8% for false positives, which doesn't match Table 3.
  - **A learned filter:** a small fine-tuned model predicted rejection at F1 0.76, while zero-shot GPT-5.1 reached only 0.06–0.24 (Table 5).
  - **How it connects:** its invalid, out-of-scope and redundant labels map onto false flags and extras. The weak zero-shot filter bears on how good an LLM judge's keep-or-dismiss call can be.
- **Agentic Code Review in the Terminal: A Trajectory-Level Analysis of Behavior, Cost, and Human-Alignment** (Charoenwet, Tantithamthavorn et al.; [arXiv 2607.16740](https://arxiv.org/abs/2607.16740), v1 18 Jul 2026; full text read):
  - **Tested:** 362 review tasks. Claude Code on Sonnet 4.6 posted 947 comments, 22.39% localised correctly and 14.37% aligned with humans. A static GPT-5.2 reviewer posted 3,180, 7.86% localised and 21.44% aligned (Table 1). Claude Code spent 51% of its cost exploring.
  - **How it connects:** per-comment precision proxies for single reviewers. No councils.
- **AgenticSCR: An Autonomous Agentic Secure Code Review for Immature Vulnerabilities Detection** (Charoenwet et al.; [arXiv 2601.19138](https://arxiv.org/abs/2601.19138), v1 27 Jan 2026, v2 3 Aug 2026; ASE 2026 Industry per the arXiv comment; abstract only):
  - **Tested:** at least 153% relative improvement in correct, relevant comments over a static LLM, a multi-agent reviewer and static analysis tools. In a shadow deployment at Atlassian, security engineers validated 54% of its comments.
  - **How it connects:** a single agent beat a multi-agent reviewer, though cost wasn't matched.
- **The Specification as Quality Gate: Three Hypotheses on AI-Assisted Code Review** (Christo Zietsman; [arXiv 2603.25773](https://arxiv.org/abs/2603.25773), v1 26 Mar 2026; full text, section 2.5):
  - **Tested:** three small sets of five planted bugs each, five runs per function. Claude caught every pattern bug. A cross-family panel caught 57 of 100, one bug was missed by all four seats, and only Gemini caught another.
  - **Two warnings for planted seeds:** hints leak through context, as when a docstring stated the convention a bug broke, and an unused import worked as a hint (removing it dropped one tool from 5 of 5 to 2 of 5).
  - **How it connects:** a second, smaller Claude-reviews-Claude planted-bug test besides Song 2026, and weaker. Its leak warnings match the easy tier's leak tags.
- **From Industry Claims to Empirical Reality: An Empirical Study of Code Review Agents in Pull Requests** (Kowshik Chowdhury et al.; [arXiv 2604.03196](https://arxiv.org/abs/2604.03196), v1 3 Apr 2026; MSR 2026 per the arXiv comment; abstract only):
  - **Tested:** PRs reviewed only by an agent were merged 45.20% of the time, against 68.37% for human-only review. 12 of 13 agents averaged below 60% "signal".
  - **How it connects:** a per-PR signal ratio, roughly the inverse of extras per catch.
- **"Go Home Copilot, You're Drunk": Developer Responses to Agent-Generated Code Review Comments** (Cynthia, Widyasari, Roy, Ting Zhang and David Lo; [arXiv 2607.21997](https://arxiv.org/abs/2607.21997), v1 24 Jul 2026, v2 29 Jul 2026; abstract only):
  - **Tested:** 54,791 comments from five agents in 342 Python repositories. The top reasons for unresolved comments were incorrect suggestions and intentional design decisions. An inline code suggestion best predicted resolution.
  - **How it connects:** resolution rate as a precision measure, like Goldman et al. in review-areas-research. The project scores against a key instead.
- **Two industry write-ups, not peer-reviewed:**
  - **[Bringing Code Review to Claude Code](https://claude.com/blog/code-review)** (Anthropic, 9 Mar 2026; full post): parallel agents, a verification step that filters false positives, and ranking by severity. It reports "less than 1% of findings are marked incorrect" and $15–25 per review, with no recall figure. Its verify step is one-way, with no appeal. Context for the Ultrareview baseline.
  - **[Same model, six code reviewers, 38% to 81% of the bugs](https://quickchat.ai/post/same-model-six-code-reviewers-38-to-81-percent-of-the-bugs)** (Quickchat AI, 13 Nov 2026; vendor; full post): six reviewer harnesses on one model, against an LLM-built key no human checked. Recall ran from 38% to 81%, so the harness mattered more than the model. A three-reviewer panel found 6 points more than one reviewer at $0.46 against $0.17 per PR. It reports cost per extra bug found, close to the project's extras-per-catch idea. Each configuration ran once.

### Judges, re-checks and appeals

- **CRJudgeBench: Can AI Detect Plausible but Invalid Code Reviews?** (Yue Pan, Jiawei Li, Ziyuan Zhang, Xiangxin Zhao and He Ye; [arXiv 2609.37216](https://arxiv.org/abs/2609.37216), v1 29 Sep 2026; under review at ICLR 2027 per the arXiv comment; abstract rechecked by the session, full text read by the subagent):
  - **Tested:** 1,199 review comments, trustworthy or not, with a 359-item test set. The best judge, the authors' own agentic Sentinel, reached 76.60% accuracy (abstract).
  - **Leniency (Tables 2–3, the subagent's read):** every model judged at least 85.52% of comments trustworthy, against a 63.79% base rate. Claude Opus 5 and GPT-5.5 were the most lenient, at 94.99%, and caught only 2.31–20.77% of untrustworthy comments.
  - **A count that doesn't add up:** section 2 says 1,031 items were reviewed by hand, but its counts sum to 829.
  - **How it connects:** the closest benchmark for the project's judge. It shows the opposite error to the one the appeal exists for.
- **Jagged Judges: Epistemic Stability Under Perturbation, Pressure, and Persistence** (Justin Zhao, Himaghna Bhattacharjee, Hannah Korevaar, Bhaktipriya Radharapu and Khalid El-Arini; [arXiv 2608.12645](https://arxiv.org/abs/2608.12645), v1 12 Aug 2026, v2 21 Aug 2026; abstract rechecked):
  - **Tested:** 9 frontier models on 14 judging tasks, none of them code. Verdicts flipped 25–71% of the time under plain pushback and 62–91% against an adversarial persuader. Pressure that changed a verdict was "almost always net-corrupting with respect to ground truth".
  - **How it connects:** an appeal is pushback on a judge. If the main session or a later seat argues with the judge, flips may be wrong more often than right. The appeal here doesn't argue with the judge directly, so this is a risk to test, not a result.
- **Who Flips? Self- and Cross-Model Counterarguments Reveal Answer Instability in LLMs** (Nikeghbal et al.; [arXiv 2606.16011](https://arxiv.org/abs/2606.16011), v1 14 Jun 2026, v2 30 Aug 2026; Findings of EMNLP 2026 per the arXiv comment; abstract only):
  - **Tested:** on MMLU, flip rates of 17.5–97.3% across 7 models. Arguments framed as the model's own raised flips by 7.1 points on average.
  - **How it connects:** a same-family appeal may sway a Claude judge more than an outside-family one. A measurable variable.
- **Are LLM Evaluators Really Narcissists? Sanity Checking Self-Preference Evaluations** (Roytburg et al.; [arXiv 2601.22548](https://arxiv.org/abs/2601.22548), v1 30 Jan 2026, v4 22 Jun 2026; ICML 2026 per the arXiv comment; abstract only):
  - **Tested:** with a baseline for the evaluator's quality, only 51% of earlier self-preference examples stay significant.
  - **How it connects:** a caveat on section 6 above. A same-family analysis should control for whether the judge could find the bug itself.
- **Quantifying and Mitigating Self-Preference Bias of LLM Judges** (Jinming Yang et al.; [arXiv 2604.22891](https://arxiv.org/abs/2604.22891), v1 24 Apr 2026, v4 2 Jun 2026; abstract only): across 20 LLMs, more capable models weren't less self-preferring. A structured, multi-dimensional evaluation cut self-preference by 31.5% on average. Weak support for the judge's fixed ruling format.
- **Reviewer Capability Governs Rejection Targeting, Not Repair Skill** (Faizan Tanveer; [arXiv 2609.04270](https://arxiv.org/abs/2609.04270), v1 2 Sep 2026; a 6-page pilot; full text): on 100 maths problems, self-review falsely rejected 18 of 52 correct answers, and a cross-family reviewer 1 of 52 (Table 2). Not code. Small evidence that same-model checkers over-reject.
- **Prior Audit-Repair Context Shifts LLM Verifier Thresholds Toward Leniency** (Parsa Mazaheri and Kasra Mazaheri; [arXiv 2608.16003](https://arxiv.org/abs/2608.16003), v1 17 Aug 2026; abstract only): an earlier audit-and-repair episode in context lowered false alarms by 2.8–11.5 points in all 15 conditions, by moving the threshold, not the ability to discriminate. An argument for keeping what the judge and appeal see fixed across configurations.
- **Chain-of-Models: Cross-Model Auditing for Bias-Robust LLM Judges** (Qian Wang et al.; [arXiv 2607.28636](https://arxiv.org/abs/2607.28636), v1; marked work in progress; abstract only): a second model audits the judge's reasoning, and a model's own bias resistance doesn't predict how good an auditor it is. The page gives a submission date of 19 May 2026, which doesn't fit its July arXiv number. Check before citing.

### Scripted workflows against agent-led orchestration

- **Deterministic vs. LLM-Controlled Orchestration for COBOL-to-Python Modernization** (Naing Oo Lwin and Rajesh Kumar; [arXiv 2605.09894](https://arxiv.org/abs/2605.09894), v1 11 May 2026; abstract rechecked, full text read by the subagent):
  - **Tested:** the same models, prompts and tools, with only who controls the steps varied. The abstract reports "comparable computational accuracy", better worst-case results and less run-to-run variation for the scripted pipeline, and up to 3.5 times fewer tokens. By the subagent's read of Table 1, LLM-controlled runs had slightly higher success rates (+0.016 to +0.034), and section 5.5 says the scripted advantage shrinks when validators are weak.
  - **How it connects:** the cleanest controlled comparison found for outside review 7's item 11. It predicts a scripted council would be cheaper and more consistent than Lite, perhaps at a small cost. It's translation, not review.
  - **From the sweep** (added 18 Nov 2026; a close-behind item; full text partly read, sections 3–5 and the limitations, through curl):
    - **Venue:** AIware 2026, per Semantic Scholar, DOI 10.1145/3805760.3814891.
    - **Claude Sonnet 4.5, Table 1:** computational accuracy 0.966 scripted against 0.964 LLM-controlled, success rate 0.902 against 0.918, CVaR0.1 0.953 against 0.949. The paper says "LLM-controlled orchestration yields higher SR across all models".
    - **Tokens:** LLM-controlled runs "often require between 1.75 million and 2.25 million tokens for complex modules", against about 400,000 to 700,000 scripted.
    - **No statistics:** there are no confidence intervals or significance tests in the sections read, and the number of runs per program wasn't found.
    - **For the project:** the winner can differ by metric, so the scripted-against-agent-led arm should report several metrics (the sweep's idea 34). Its paired-CI design would be a step up from this paper's.
- **Agent Architecture Cost-Success Trade-offs: A Controlled Evaluation across Enterprise-Style SOPs** (Subhrangshu Nandi et al.; [arXiv 2611.12953](https://arxiv.org/abs/2611.12953), v1 7 Nov 2026; abstract only): no architecture won in aggregate. Coordinated set-ups cost 1.4–4.7 times the tokens of a single agent, and a plausible multi-agent build lost to it. Only a targeted redesign beat it. So how well a council is built may matter more than its shape.
- **Abstract only, briefly:**
  - **LLM-as-Code: Agentic Programming for Agent Harness** (Junjia Qi et al.; [arXiv 2606.15874](https://arxiv.org/abs/2606.15874), v3 9 Nov 2026; KDD 2026 AgenticSE workshop): a position paper arguing that code, not the model, should own the loop. No figures.
  - **In-Context Prompting Obsoletes Agent Orchestration for Procedural Tasks** (Simon Dennis et al.; [arXiv 2604.27891](https://arxiv.org/abs/2604.27891), v2 5 May 2026; LLM-judged): cuts the other way. The whole procedure in one prompt beat a LangGraph orchestration.
  - **Multi-Agent Teams Hold Experts Back** (Pappu et al.; [arXiv 2602.01011](https://arxiv.org/abs/2602.01011), v4 28 May 2026; ICML 2026 per the arXiv comment): self-organising teams did up to 41.1% worse than their best member, compromising instead of deferring to the expert. Bears on the free-debate arm of outside review 7's item 8, and on judged against consensus combining.

### Project instruction files (CLAUDE.md, AGENTS.md)

None of these tests reviewers. Each is about coding agents.

- **Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?** (Thibaud Gloaguen, Niels Mündler-Sasahara, Mark Niklas Müller, Veselin Raychev and Martin Vechev; [arXiv 2602.11988](https://arxiv.org/abs/2602.11988), v1 12 Feb 2026, v3 29 Sep 2026; abstract rechecked, full text read by the subagent):
  - **Tested:** context files "do not generally improve task success rates" and raise cost by over 20% (abstract). Agents do follow the instructions in them. By the subagent's read of section 4.2, developer-written files beat LLM-written ones by about 7 points, the one significant comparison.
  - **How it connects:** the main precedent for the help-or-bias test's "help" side.
  - **The sweep's figures don't match the "about 7 points" above** (added 18 Nov 2026). The sweep read sections 3–4.3 of the v3 full text through curl. It gives developer-written files as improving performance "by 2.4% on average (p=21%)", against a drop of 0.5% and 2% for LLM-written files on SWE-bench and CTXbench. It also says developer-written files "improve performance for all agents but Claude Code". Those figures don't give a 7-point gap between developer-written and LLM-written files. Check the paper before citing either. The point that Claude Code is the exception matters directly for the `CLAUDE.md` arm.
- **Stale Instruction Files Override the Code in Coding Agents: A One-Sentence Fix** (Xiaonan Xu and Wenjing Wu; [arXiv 2610.30571](https://arxiv.org/abs/2610.30571), v1 22 Oct 2026; abstract rechecked, full text read by the subagent):
  - **Tested:** 40 Python projects with a planted conflict between the instruction file and the code, 320 runs on Claude Code and Codex CLI. 90.1% of choices followed the stale file. Claude Code named the conflict in 79 of 80 runs and still followed the file. One sentence about precedence moved choices following the code from 4.2% to 91.4%.
  - **How it connects:** the closest design for the test's "bias" side. A reviewer that reads a wrong `CLAUDE.md` may excuse a bug that fits it, or flag correct code. That's an inference: the paper doesn't test reviewers.
  - **From the sweep** (added 18 Nov 2026; a close-behind item; abstract read, verbatim, arXiv API):
    - **More detail:** Codex "rewrote the existing code to match the file in 20 of 80 runs". The mechanism offered is that "the instruction file reaches the model as an instruction and the code as tool output, which models are trained to rank lower".
    - **Data and venue:** the data is at github.com/WenJing95/stale-docs-data, and the paper is "Submitted to SN Computer Science".
    - **For the project:** the sweep suggests a "stale or wrong `CLAUDE.md`" condition, measuring false alarms and misses separately (its idea 33). It also bears on the docs' statement that Code Review turns `CLAUDE.md` violations into findings.
- **Guardrails Beat Guidance: A Large-Scale Study of Rules, Skills, and Persistent Configuration for Coding Agents** (Xing Zhang et al.; [arXiv 2604.11088](https://arxiv.org/abs/2604.11088), v2 28 May 2026; full text): random and curated `CLAUDE.md` rules both scored 63.8% against a 50.0% baseline on 58 tasks, with no significant difference between conditions. The authors put the gain down to priming that doesn't depend on content. So a CLAUDE.md test needs a random-file control, not just with and without.
  - **From the sweep** (added 18 Nov 2026; a close-behind item; abstract read, verbatim, arXiv API; full text partly read, the method and the sections on priming and limitations):
    - **Scale:** 679 scraped rule files (25,532 rules) and over 5,000 Claude Code runs on Claude Opus 4.6.
    - **Which rules help:** "every individually beneficial rule is a negative constraint ... while every individually harmful one is a positive directive".
    - **Task selection:** the 58 tasks were chosen as those solved 1 or 2 times out of 3, which leaves room for regression to the mean.
    - **Baseline noise:** the no-rule baseline was 50.0% in one experiment and 60.3% in another. That supports paired same-seed CIs.
    - **For the project:** the sweep suggests a length-matched placebo `CLAUDE.md` (its idea 33), and treating "negative constraints help" as a hypothesis for how seat briefs are written.
- **Do Context Files Help Coding Agents? A Two-Agent Ablation Study** (Prakhar Khatri; [arXiv 2607.27250](https://arxiv.org/abs/2607.27250), v1 28 Jul 2026; full text): no measurable effect on 15–17 tasks, and a power analysis saying 120–200 tasks are needed to detect 10 points. Useful for sizing the test.
- **Abstract only, briefly:**
  - **On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents** (Jai Lal Lulla et al.; [arXiv 2601.20404](https://arxiv.org/abs/2601.20404), v2 30 Mar 2026): lower runtime and output tokens with a file, which partly contrasts with Gloaguen et al.'s higher cost.
  - **Instruction Adherence in Coding Agent Configuration Files** (Damon McMillan; [arXiv 2605.10039](https://arxiv.org/abs/2605.10039), v1 11 May 2026): 1,650 Claude Code sessions, with no detectable effect of file size, position or contradictions on compliance.
  - **When Instruction Files Go Stale** (Tural Mehtiyev et al.; [arXiv 2611.09802](https://arxiv.org/abs/2611.09802), v1 6 Nov 2026): a stale test command cost extra tool calls, and no agent repaired the file.
  - **SWE-PRBench** (Deepak Kumar; [arXiv 2603.26130](https://arxiv.org/abs/2603.26130), v1 27 Mar 2026): the code-review benchmark Adversarial Review used. (amended 18 Nov 2026, from the sweep, and confirmed by a Claude Code subagent on arXiv: its abstract describes "350 pull requests", against the 100 in the Adversarial Review entry.) A review-specific sign that extra context, instruction files included, can dilute attention.

Connection: a vendor stance for precision ("Silence is better than noise"), while independent work finds a 72.9% thread-resolution rate (Go Home Copilot) and missed security flaws (Amro and Alalfi).
- **OpenAI Codex code review: A Practical Approach to Verifying Code at Scale** (Maja Trębacz et al. with the Codex team, OpenAI Alignment blog; 1 Dec 2025; vendor research post, not peer-reviewed; https://alignment.openai.com/scaling-code-verification/; page read (fetch tool)): a trained agentic reviewer with repository tools and execution comments on 36% of Codex-generated PRs, where "46% of those comments lead to a code change, versus 53% for comments on human-written PRs", with precision and recall judged by humans and the stance that "Precision is more important for usability than recall" (quoted by the fetch tool). Connection: supports weighting precision in the council score, and its faster drop on model-generated code at smaller budgets bears on the same-family and effort arms.
- **Introducing Qodo 2.0** (Qodo; 4 Feb 2026; vendor marketing; https://www.qodo.ai/blog/introducing-qodo-2-0/; page read (fetch tool)): describes "a multi-agent expert review architecture" with dedicated context per agent, a judge agent that resolves conflicts, removes duplicates and filters low-signal results and findings "organized by severity", claiming "highest overall F1 score at 60.1%" and "highest recall at 56.7%" (the post later gives an exhaustive mode the same 60.1). Connection: the project's council shape (specialists, a judge and severity) already exists as a product, though with no equal-cost comparison, appeal or evolution.
- **We benchmarked Claude's code review tool** ("Qodo Research | March 2026", posted by Nnenna Ndukwe; 12 Mar 2026; vendor marketing; https://dev.to/nnennandukwe/we-benchmarked-claudes-code-review-tool-heres-what-the-data-shows-35b9; page read (fetch tool)): on "100 PRs with 580 injected issues across 8 production-grade open-source repositories" with one LLM judge for all tools, Qodo Extended scored P 79% / R 71% / F1 74.7%, Qodo Default 79/60/68.2 and Claude Code Review 79/52/62.7 at "$15–$25 per review". Connection: the only published number pitting Anthropic's managed review against a specialist-plus-judge council on injected bugs, but vendor-run, so equal precision with lower recall is a hypothesis the project could test independently.
- **Greptile benchmarks** (Greptile; evaluation "conducted in July 2025"; vendor; https://www.greptile.com/benchmarks; page read (fetch tool)): 50 real bugs from Sentry, Cal.com, Grafana, Keycloak and Discourse were traced to their introducing commits and reintroduced as fresh PRs in clean forks, and catch rates were Greptile 82%, Bugbot 58%, Copilot 54%, CodeRabbit 44% and Graphite 6%, with no false-positive counts (the fetch tool notes Copilot's per-repository counts sum to 26/50, 52%). Connection: a small, self-run SZZ-style reintroduced-bug seed design, which Augment and Luxor later rescored.
- **Greptile v4 + New Pricing** (Daksh Gupta; 5 Mar 2026; vendor; https://www.greptile.com/blog/greptile-v4; page read (fetch tool)): an A/B test over "hundreds of thousands of PRs" raised addressed comments per PR from 0.92 to 1.60 and the share addressed from 30% to 43%, with "addressed" "determined by an LLM", at $30 per developer per month including 50 reviews, then $1 per review. Loosely related: an LLM-decided uptake measure with no architecture described, so not comparable with a planted key.
- **The art and science of context engineering for AI code reviews** (Amitosh Swain, CodeRabbit; 16 Jul 2025; vendor; https://www.coderabbit.ai/blog/the-art-and-science-of-context-engineering; page read (fetch tool)): describes context from "dozens of sources", different prompts and models by complexity, verification agents that validate and improve review comments and "an ensemble of models instead of relying on a single model", with no severity scheme or precision or acceptance figures. Connection: an ensemble with a verification layer in production, but with no published evidence to compare a council against.
- **The more AI writes the code, the more review needs independence** (Yiwen Xu and Li Ye, CodeRabbit; 17 Jun 2026; vendor; https://www.coderabbit.ai/blog/code-review-needs-independence; page read (fetch tool)): argues that reviewers should be independent of the authoring model (a "Homogenization Trap"), citing Bugbot defaulting to Cursor's own Composer model, with second-hand supporting numbers that were not checked. Connection: a vendor argument for the same-family concern and the mixed-family arm, with no data of its own.
- **Google Gemini Code Assist on GitHub** (Google; official docs, no dates; https://docs.cloud.google.com/gemini/docs/code-review/review-repo-code and https://docs.cloud.google.com/gemini/docs/code-review/customize-repo-review; page read (fetch tool)): PR summaries plus review comments with an explicit `comment_severity_threshold` (default MEDIUM; values LOW, MEDIUM, HIGH, CRITICAL), unlimited comments by default, optional per-repository memory and no accuracy figures, while CR-Bench-v2 reports it detects 8.1% of known defects. Connection: a user-facing severity threshold is the product analogue of the judge's severity ruling.
- **Security study of Copilot review: GitHub's Copilot Code Review: Can AI Spot Security Flaws Before You Commit?** (Amena Amro and Manar H. Alalfi; arXiv preprint, 17 Sep 2025; [arXiv 2509.13650](https://arxiv.org/abs/2509.13650); abstract read (verbatim, arXiv API)): on labelled vulnerable samples, Copilot code review "frequently fails to detect critical vulnerabilities" such as SQL injection and XSS, and its feedback mostly addresses low-severity issues, with no figures in the abstract. Connection: independent evidence that a vendor single reviewer misses severe bugs, which bears on security seeds and severity scoring.

#### 2.3 Debate against independent judging

- **Talk Isn't Always Cheap: Understanding Failure Modes in Multi-Agent Debate** (Andrea Wynn et al.; ICML 2025 Workshop on Multi-Agent Systems, per the arXiv comment; v1 5 Sep 2025, v2 13 Oct 2025; [arXiv 2509.05396](https://arxiv.org/abs/2509.05396); abstract read (verbatim, arXiv API); full text partly read (fetch tool; results tables and discussion)): debate among GPT-4o-mini, Llama-3.1-8B and Mistral-7B in homogeneous and mixed teams "can lead to a decrease in accuracy over time" even when stronger models outnumber weaker ones (CommonSenseQA fell in every configuration, for example 58.2 → 50.2), and a correctness-payoff prompt did not significantly reduce answer flips. Connection: supports keeping reviewers independent until the judge and challenges a debating council of families that differ in strength.
- **Kenton et al.: On scalable oversight with weak LLMs judging strong LLMs** (Zachary Kenton et al., Google DeepMind; arXiv v1 5 Jul 2024, v2 12 Jul 2024, no venue on the arXiv page and NeurIPS 2024 commonly given but not confirmed; [arXiv 2407.04622](https://arxiv.org/abs/2407.04622); abstract read (verbatim, arXiv API); full text partly read (fetch tool; results and summary sections, first 100k of 155k characters)): comparing debate, consultancy and direct QA with weaker judges, debate beat direct QA in extractive QA with information asymmetry but results were mixed elsewhere, and for the strongest judge on closed tasks "debate actually leads to worse judge accuracy than QA without article" (fetch-tool quote). Connection: the council's judge can read the code, the case without information asymmetry, so debate is better framed as an aid to the judge than as a replacement for independent findings.
- **Khan et al.: Debating with More Persuasive LLMs Leads to More Truthful Answers** (Akbir Khan et al.; arXiv v1 9 Feb 2024, v4 25 Jul 2024, ICML 2024 widely reported but venue not confirmed; [arXiv 2402.06782](https://arxiv.org/abs/2402.06782); abstract read (verbatim, arXiv API)): on QuALITY, two expert debaters with the story helped non-expert models and humans reach "76% and 88% accuracy respectively (naive baselines obtain 48% and 60%)". Loosely related: debate helps a judge who can't read the source, which the project's judge can, though it could justify a cheaper limited-context judge for disputed findings (untested on code).
- **Not All Flips Are Conformity: Decomposing Stance Convergence in Multi-Agent LLM Debate** (Xiqi Hao et al.; arXiv preprint, v1 30 May 2026, v2 18 Oct 2026; [arXiv 2606.00820](https://arxiv.org/abs/2606.00820); abstract read (verbatim, arXiv API)): with five GPT-4o agents on MMLU-Pro, "37% of agent-question pairs change even without peer information", and full reasoning gave no majority-vote gain over self-reflection "while using 57% more tokens". Connection: a matched "re-think alone" control is worth copying for the debate arm, and agreement between seats is an ambiguous confidence signal.
- **When Debate Helps: Proposal Supply and Verification-Aware Readout in Multi-Agent Reasoning** (Zihao Zhao et al.; arXiv preprint, v1 3 Oct 2026; [arXiv 2610.04686](https://arxiv.org/abs/2610.04686); abstract read (verbatim, arXiv API)): argues debate beats voting only when some agent proposes the right answer ("proposal supply") and the read-out picks it when voting misses it, with coverage-selected societies improving accuracy at matched budgets (qualitative only in the abstract). Connection: in a council the proposal supply is the union of seat findings and the read-out is the judge plus appeal, so the project could report seeds found by at least one seat but lost at the judge and how many the appeal wins back.
- **The Cost of Consensus: Isolated Self-Correction Prevails Over Unguided Homogeneous Multi-Agent Debate** (Blaž Bertalanič and Carolina Fortuna; ACM Conference on AI and Agentic Systems per the arXiv comment, not otherwise confirmed; v1 29 Apr 2026; [arXiv 2605.00914](https://arxiv.org/abs/2605.00914); abstract read (verbatim, arXiv API)): teams of 10 homogeneous 7–8B agents showed conformity up to 85.5%, plurality voting discarded correct answers already in the pool ("oracle gap up to 32.3 percentage points") and debate used "2.1-3.4× more tokens" than self-correction "for equal or lower accuracy". Connection: supports independent review, and voting that throws away correct answers already raised is the loss the appeal is meant to recover at the judge.
- **Statistical Scouting: Statistical Scouting Finds Debate-Safe but Not Debate-Useful Cases: A Matched-Ceiling Study of Open-Weight LLM Reasoning Protocols** (Julia Hu et al.; arXiv technical report, v1 10 May 2026; [arXiv 2605.09618](https://arxiv.org/abs/2605.09618); abstract read (verbatim, arXiv API)): under a matched cap of 960 generated tokens on MuSiQue and GSM8K, "each (model, dataset) cell has a different winner", cheap vote-entropy routing gained only +1.3 and +1.7 pp and "66% of debate-helpful examples (31/47) occur when voting is unanimous but wrong". Connection: agreement among seats is not evidence that a finding or a miss is right, which argues for an appeal not triggered only by disagreement.
- **Peacemaker or Troublemaker: How Sycophancy Shapes Multi-Agent Debate** (Binwei Yao et al.; arXiv preprint (Semantic Scholar venue: arXiv), v1 27 Sep 2025; [arXiv 2509.23055](https://arxiv.org/abs/2509.23055); abstract read (verbatim, arXiv API)): measured inter-agent sycophancy separately for debaters and judges and found it "yields lower accuracy than single-agent baselines" through debater-driven and judge-driven failure modes (no figures in the abstract). Connection: a judge that defers to the most confident or most numerous seats is a separate risk, so the project could log how often the judge sides with a seat majority against the key.
- **When Identity Skews Debate: Anonymization for Bias-Reduced Multi-Agent Reasoning** (Hyeong Kyu Choi et al.; ACL 2026 Main per the arXiv comment; v1 8 Oct 2025, v5 9 Apr 2026; [arXiv 2510.07517](https://arxiv.org/abs/2510.07517); abstract read (verbatim, arXiv API)): modelling debate as an identity-weighted Bayesian update, it found "identity bias is widespread, with sycophancy far more common than self-bias" and proposes removing identity markers. Connection: the judge and appeal agent should rule on findings stripped of seat names, roles and model family.
- **Silent Dissent: LLM Agents That Yield to the Majority Still Represent Their Original Premise** (Ziang Ni and Peng Zou; arXiv preprint, v1 2 Oct 2026, v2 5 Oct 2026; [arXiv 2610.02702](https://arxiv.org/abs/2610.02702); abstract read (verbatim, arXiv API)): agents that gave in to scripted unanimous peers still represented their original premise internally (hit@100 0.85, 0.22 and 0.24 for three models), and hiding the agent's own earlier answer made Qwen3.5-4B give in on 89% of questions instead of 8%. Loosely related: conformity is very sensitive to what an agent is shown, which bears on whether the appeal agent sees the judge's reasons.

#### 2.4 Diversity of LLM judges, and correlated errors

- **LLMs as a Jury: Cross-Model Consensus Can Outperform Process Reward Models for LLM Reasoning** (Ning Liu; arXiv preprint, v1 11 Jul 2026, v3 17 Aug 2026; [arXiv 2607.10139](https://arxiv.org/abs/2607.10139); abstract read (verbatim, arXiv API)): agreement among independently trained models each answering once closed "the entire gap to an oracle selector" on competition maths, with a law predicting consensus accuracy "to a mean absolute error of 0.03" and a ceiling at a shared-error floor. Connection: supports the mixed-family arm on single-answer tasks, and the shared-error floor is what the project should estimate for its seats on seeds, though open-ended bug finding makes consensus a weaker signal.
- **State-dependent error correlations shape voting thresholds in committees of AI agents** (Haifeng Li and Mo Hai; arXiv preprint, v1 27 Jul 2026; [arXiv 2607.23931](https://arxiv.org/abs/2607.23931); abstract read (verbatim, arXiv API)): from 174,384 votes by 28 LLMs on four binary-screening benchmarks, shared errors "create a positive asymptotic error floor for majority voting", a dependence model raised R² "from 0.840 under independence to 0.967" and the overall reduction from majority was 15.73% (95% bootstrap CI 13.41–16.75%). Connection: the council's aggregation rule should be tuned against the cost of misses and false alarms, not fixed at a majority.
- **Shared Item-Level Error Limits the Aggregation of Small Language Models in Fermi Estimation** (Carolina Fortuna and Blaž Bertalanič; arXiv preprint, v1 12 Nov 2026; [arXiv 2611.16315](https://arxiv.org/abs/2611.16315); abstract read (verbatim, arXiv API)): across 2.51M answers by 15 open models, the shared item-level component took "a median 0.906 of the error variance", teams of thirty cut a single agent's error by a median 1.7%, three debate rounds cut dispersion by 93% but left shared error unchanged and no mixture beat the most accurate model. Connection: copies of one model add little and debate removes disagreement but not shared error, while mixing helped against homogeneous teams but never beat the best model.
- **Vibe Coding on Trial: Operating Characteristics of Unanimous LLM Juries** (Muhammad Aziz Ullah and Abdul Serwadda; submitted to IEEE ICSC 2026 per the arXiv comment, acceptance not confirmed; v1 12 Feb 2026, v2 22 Aug 2026; [arXiv 2602.18492](https://arxiv.org/abs/2602.18492); abstract read (verbatim, arXiv API)): on 82 MySQL text-to-SQL tasks with execution-based ground truth, small unanimous committees of strong models cut false accepts while still passing many good queries, and committee composition mattered significantly (no figures in the abstract). Connection: on findings a unanimity rule would drop real bugs, which is the case for an appeal under consensus combining.
- **DVDR-LLM: Diverse LLMs vs. Vulnerabilities: Who Detects and Fixes Them Better?** (Arastoo Zibaeirad and Marco Vieira; arXiv preprint, v1 14 Dec 2025; [arXiv 2512.12536](https://arxiv.org/abs/2512.12536); abstract read (verbatim, arXiv API)): an agreement-threshold ensemble of diverse LLMs gave "10-12% higher detection accuracy" than the average individual model and, for multi-file vulnerabilities, recall +18% and F1 +11.8%, while trading fewer false positives in verification for more false negatives in detection. Connection: supports mixed-model ensembles for bug finding, but measured against the average member rather than the best, and its trade-off between misses and false alarms is the one the judge and appeal manage.
- **Sun et al.: Ensembling Large Language Models for Code Vulnerability Detection: An Empirical Evaluation** (Zhihong Sun et al.; arXiv preprint, v1 16 Sep 2025, v2 18 Sep 2025; [arXiv 2509.12629](https://arxiv.org/abs/2509.12629); abstract read (verbatim, arXiv API)): bagging, boosting and stacking over five small code LLMs on Devign, ReVeal and BigVul found ensembles "can significantly improve detection performance" and noted discrepancies among architecturally distinct LLMs (no other figures in the abstract). Loosely related: complementarity between code models, but from fine-tuned function-level classifiers far from agentic review.
- **Don't Always Pick the Highest-Performing Model: An Information Theoretic View of LLM Ensemble Selection** (Yigit Turkmen et al.; arXiv preprint, v1 8 Feb 2026; [arXiv 2602.08003](https://arxiv.org/abs/2602.08003); abstract read (verbatim, arXiv API)): choosing ensemble members by greedy mutual information with the true label, with correlated errors modelled by a Gaussian copula, "consistently outperforms strong baselines under the same query budget" on MedMCQA, MMLU and IMDB (no figures in the abstract). Loosely related: supports choosing seats for what they add given the others, which the evolution's mutation step could use.
- **Exposing Vulnerability Monoculture Through Systemic Adversarial Robustness** (Leo Elmecker-Plakolm et al.; arXiv preprint, v1 19 Oct 2026; [arXiv 2610.27353](https://arxiv.org/abs/2610.27353); abstract read (verbatim, arXiv API)): measuring how many distinct attacks are needed to compromise a pool of models, it found pools distilled from DeepSeek-R1 and Claude Opus 4.6 less systemically robust than their parent pools (no figures in the abstract). Loosely related: a "mixed-family" council of models distilled from Claude may not really be mixed.

#### 2.5 Planted-bug and mutation benchmarks, and their contamination

- **SWE-smith: Scaling Data for Software Engineering Agents** (John Yang et al.; arXiv preprint, v1 30 Apr 2025, v2 21 May 2025, venue not confirmed; [arXiv 2504.21798](https://arxiv.org/abs/2504.21798); abstract read (verbatim, arXiv API)): a pipeline that synthesises test-breaking task instances for any Python repository gave "50k instances sourced from 128 GitHub repositories", and SWE-agent-LM-32B trained on it reached "40.2% Pass@1" on SWE-bench Verified. Connection: the largest public generator of synthetic bugs, but BugPilot's analysis finds its bugs small (about 1.2 files and 8.8 lines) and skewed to logic and conditional faults, which bears on the mutation and Claude-written seed arms.
- **SMART: Boosting LLMs for Mutation Generation** (Bo Wang et al.; arXiv preprint, v1 25 Mar 2026, "to be published in the collection of FSE 2026" per the arXiv comment; [arXiv 2603.24560](https://arxiv.org/abs/2603.24560); abstract read (verbatim, arXiv API)): retrieval over real bugs, focused code chunking and fine-tuning raised mutant validity "from 42.89% to 65.6%" and reached a "real bug detection rate of 92.61% (vs. 57.86% for LLMut)" on 1,991 real Java bugs. Connection: plain LLM mutants are often invalid or duplicated, which bears on Claude-written seeds and on dropping near-duplicates, though its "real bug detection rate" is a coupling measure, not review recall.
- **Test-aware mutant generation: Beyond Rule-Based Mutation Testing: Test-Aware Mutant Generation Using Large Language Models** (Nils Kiele et al.; arXiv preprint, 24 Sep 2026, "Accepted to ESEM 2026" per the arXiv comment; [arXiv 2609.35841](https://arxiv.org/abs/2609.35841); abstract read (verbatim, arXiv API)): giving the LLM the problem, the correct solution and the base tests and asking for a mutant that still passes them gave "verified fault rates of 87.7% (HumanEval) and 79.1% (MBPP)", against "12.2% and 23.0%" for test-blind prompting and "4.4% and 5.7%" for mutmut. Connection: a cheap validity check for Claude-written seeds (pass the existing tests, fail a stronger oracle), though on toy benchmarks only.
- **MegaBugFix: Diff-Based Code Corruption using LLMs for Large-Scale Bugfix Benchmarking** (Balázs Szalontai et al.; arXiv preprint, v1 27 Jun 2026, v3 1 Jul 2026, venue not confirmed; [arXiv 2606.29088](https://arxiv.org/abs/2606.29088); abstract read (verbatim, arXiv API)): a fine-tuned LLM writes bug injections as diffs into correct Python programs, giving "12,629 buggy Python programs" on which 13 open-weight models do worse than on existing bug-fix benchmarks. Connection: it names "overly simplistic bugs" as a pitfall of naive LLM injection, and its motivation matches decision 6's points on seed counts and near-duplicates, though it is about repair, not review.
- **BugFarm: Challenging Bug Prediction and Repair Models with Synthetic Bugs** (Ali Reza Ibrahimzada et al.; v1 3 Oct 2023, v3 9 Sep 2025, "Published in SCAM 2025" per the arXiv comment; [arXiv 2310.02407](https://arxiv.org/abs/2310.02407); abstract read (verbatim, arXiv API)): an LLM mutates code where a learned bug predictor attends least, giving 435k+ hard-to-detect bugs from 1.9M mutants. Connection: a warning that planted bugs can be made adversarial to a detector, so a Claude planter could place bugs where Claude reviewers look least or most, which argues for seeds whose placement Claude doesn't choose.
- **Mutant realism in deep learning: An Empirical Study of the Realism of Mutants in Deep Learning** (Zaheed Ahmed et al.; arXiv preprint, v1 18 Dec 2025, v2 12 Oct 2026, venue not confirmed; [arXiv 2512.16741](https://arxiv.org/abs/2512.16741); abstract read (verbatim, arXiv API)): a statistical framework scores mutant realism by "coupling strength and behavioral similarity to real faults" for deep-learning mutation tools on four real-bug datasets. Loosely related: a reusable way to compare Claude-written seeds, mutants and SZZ bugs for realism, though from another domain.
- **Meta ACH: Mutation-Guided LLM-based Test Generation at Meta** (Christopher Foster et al.; arXiv preprint, 22 Jan 2025, "Submitted to FSE 2025 Industry Track" per the arXiv comment, acceptance not confirmed; [arXiv 2501.12862](https://arxiv.org/abs/2501.12862); abstract read (verbatim, arXiv API)): an LLM generated "9,095 mutants and 571 privacy-hardening test cases" over 10,795 Kotlin classes, with an equivalent-mutant detector at "precision of 0.79 and a recall of 0.47 (rising to 0.95 and 0.96 with simple pre-processing)" and engineers accepting "73% of its tests". Connection: supports concern-targeted seeds like the project's role-specific ones, and its equivalent-mutant detector addresses seeds that don't change behaviour and so give free false misses.
- **Learned or Memorized: Learned or Memorized ? Quantifying Memorization Advantage in Code LLMs** (Djiré Albérick Euraste et al.; arXiv preprint, 15 Apr 2026, "Accepted at ICSE 2026 (to appear)" per the arXiv comment; [arXiv 2604.13997](https://arxiv.org/abs/2604.13997); abstract read (verbatim, arXiv API)): a perturbation measure of memorisation advantage across 8 open code LLMs and 19 benchmarks found "CVEFixes remains below 0.1, and Defects4J is lower than other program repair benchmarks". Connection: challenges a flat "contamination: high" for Defects4J, since exposure and score inflation are different things, though for open models only.
- **BenchChecker: Assessing the Credibility of Bug-Fixing Benchmarks for LLMs** (Di Wu et al.; USENIX Security 2026, pp. 5077–5096, per the arXiv `journal_ref`; arXiv 14 Oct 2026; [arXiv 2610.19447](https://arxiv.org/abs/2610.19447); abstract read (verbatim, arXiv API)): a two-stage black-box contamination detector for bug-fix benchmarks reached "AUC scores around 0.9 across six benchmarks", and filtering contaminated samples cut most LLMs' reported resolution rates "by more than 20%" on medium-difficulty tasks. Connection: supports a cheap filter for SZZ seeds (fix commit after the reviewing model's cutoff), though validated on open models only.
- **SWE-Verified memory: Does SWE-Bench-Verified Test Agent Ability or Model Memory?** (Thanosan Prathifkumar et al.; arXiv preprint, v1 11 Dec 2025, v2 22 Dec 2025, the HTML page lists the International Workshop on Agentic Engineering, April 2026 (fetch tool), acceptance not confirmed; [arXiv 2512.10218](https://arxiv.org/abs/2512.10218); abstract read (verbatim, arXiv API); full text partly read (fetch tool: Tables 3 and 4)): asked to name the files to edit from issue text alone, Claude 3.5 Sonnet got 65% on SWE-bench Verified against 12.2% on BeetleBox and 12% on SWE-rebench (fetch tool, Table 3), and the abstract says models were "3 times better" on Verified. Connection: direct evidence that Claude has memorised public bug benchmarks, and a cheap probe the project could run on its own candidate seeds.
- **Measurement-first audit: Measurement-First Auditing of Agentic Leaderboards: Contamination Susceptibility, Matched-Control Re-evaluation, and Scorer Validation** (Dishu Yang et al.; NeurIPS 2026 Workshop LCFM per the arXiv `journal_ref`; arXiv 5 Oct 2026; [arXiv 2610.05830](https://arxiv.org/abs/2610.05830); abstract read (verbatim, arXiv API)): coding three contamination channels found "none of the 27 channel assessments was coded closed", a matched-control re-test of the SWE-bench Verified localisation gap gave GPT-4.1 "a +10.0-point" gap with 95% intervals that included zero and the reproduction scorer failed its validation gate. Connection: a template for the project's contamination check, naming live channels for a Claude Code council (web search, git history) and validating the scorer before trusting it.
- **Cross-Context Verification (CCV): Hierarchical Detection of Benchmark Contamination through Session-Isolated Analysis** (Tae-Eun Song; arXiv preprint, v1 23 Mar 2026, v2 1 Apr 2026, venue not confirmed; [arXiv 2603.21454](https://arxiv.org/abs/2603.21454); abstract read (verbatim, arXiv API)): solving each problem in isolated sessions separated recall from reasoning with perfect separation "On 9 SWE-bench Verified problems (45 trials, Claude Opus 4.6, temperature 0)", found "33% of prior contamination labels are false positives" and a Worker to Verifier to Director pilot gave "100% sycophantic confirmation". Connection: a Claude-specific contamination probe for seeds, and its side findings (sequential verifiers confirming sycophantically, repeated review adding false positives faster than true catches) bear on the sequential and appeal arms, though n is very small; the sweep's Part 1 names it as title and metadata only.
- **SchrodingerRepo: Schrödinger's Code Repository: Have LLMs Learned SWE-bench or Memorized It?** (Silin Chen et al.; arXiv preprint, 21 Aug 2026, venue not confirmed; [arXiv 2609.27891](https://arxiv.org/abs/2609.27891); abstract read (verbatim, arXiv API)): rewriting the test repository at evaluation time (problem statement, namespaces, layout and behaviour-preserving edits) "consistently degrades agent performance and substantially increases interaction costs" (no figures in the abstract). Connection: a decontamination option for public seeds, with the warning that rewritten and unrewritten seeds should not be pooled.
- **SWE-Bench+: Enhanced Coding Benchmark for LLMs** (Reem Aleithan et al.; arXiv preprint, 9 Oct 2024 (v2 10 Oct 2024), venue not confirmed; [arXiv 2410.06992](https://arxiv.org/abs/2410.06992); abstract read (verbatim, arXiv API)): "32.67% of the successful patches involve cheating" because solutions were in the issue or its comments and "31.08% of the passed patches are suspicious patches due to weak test cases", with filtered resolution dropping "from 12.47% to 3.97%". Connection: solution leakage through PR or issue text means seed PRs need neutral descriptions, the other side of When AI Agrees Too Much (descriptions can leak or hide).
- **SWE-rebench V2** (Ibragim Badertdinov et al.; "ICML 2026" per the arXiv comment; v1 27 Feb 2026, v2 1 Jun 2026; [arXiv 2602.23866](https://arxiv.org/abs/2602.23866); abstract read, verbatim, arXiv API): "32,079 tasks spanning 20 languages and 3,617 repositories" plus "120,000+ tasks", filtered by an ensemble of LLM judges validated against human SWE-bench annotations. Connection: answers the seed-sources doc's open note, since v2 is language-agnostic (per-language counts not confirmed), though it is a training collection, not a moving-window leaderboard.
- **SWE-MERA** (Pavel Adamenko et al.; "EMNLP 2025" per the arXiv comment; v1 15 Jul 2025, v3 11 Jul 2026; [arXiv 2507.11059](https://arxiv.org/abs/2507.11059); abstract read, verbatim, arXiv API): a "dynamic, continuously updated benchmark" with about 10,000 potential tasks and 728 samples available, collected between September 2024 and June 2025. Loosely related: another refreshed Python issue collection, of low relevance beyond SWE-bench-Live.
- **Saving SWE-Bench** (Spandan Garg et al.; "Accepted at CAIN 2026" per the arXiv comment; [arXiv 2510.08996](https://arxiv.org/abs/2510.08996); abstract read, verbatim, arXiv API): rewriting formal issues as realistic chat-style queries showed benchmarks "overestimate agent capabilities for some models by >50%" on public benchmarks and "~10-16%" on a private C# benchmark. Loosely related: input framing moves scores a lot, which bears on how much context (PR text, `CLAUDE.md`) a seed comes with.

#### 2.6 SZZ and escaped-bug datasets

- **Agentic SZZ on the Linux kernel: LLM-Based Agents for Identifying Bug-Introducing Commits** (Niklas Risse and Marcel Böhme; arXiv v1 31 Mar 2026, v2 23 Sep 2026, "Accepted at ... ASE '26. - **RovoDev Code Reviewer: A Large-Scale Online Evaluation of LLM-based Code Review Automation at Atlassian** (Kla Tantithamthavorn et al.; arXiv v1 3 Jan 2026, v2 20 Jan 2026, "Accepted at ... #### 2.8 Appeal and re-check steps

- **TinyV: Reducing False Negatives in Verification Improves RL for LLM Reasoning** (Zhangchen Xu et al.; arXiv preprint, no venue on the arXiv page, v1 20 May 2025, v2 22 May 2025; [arXiv 2505.14625](https://arxiv.org/abs/2505.14625); abstract read (verbatim, arXiv API)): "over 38% of model-generated responses suffer from false negatives" under a rule-based maths answer checker, and a small LLM verifier that re-examines only rejected answers "boosts pass rates by up to 10%". #### 2.11 Human-in-the-loop costs of AI review

- **Human-AI Synergy: Human-AI Synergy in Agentic Code Review** (Suzhen Zhong et al.; arXiv preprint, v1 16 Mar 2026, v3 30 Oct 2026, no venue stated; [arXiv 2603.15911](https://arxiv.org/abs/2603.15911); abstract read (verbatim, arXiv API); full text read (fetch tool, 100k of 103k characters)): across 278,790 review conversations in 300 projects, AI agents' suggestions were adopted at "16.6% vs. 56.5%" for human reviewers (fetch tool, from the v3 abstract in the HTML full text), 28.7% of a sample of 383 unadopted AI suggestions were incorrect or would break the code and humans "exchange 11.8% more rounds" when reviewing AI-generated code. #### 2.12 Prompt evolution and self-improving agent set-ups

- **Meta-Agent Challenge: The Meta-Agent Challenge: Are Current Agents Capable of Autonomous Agent Development?** (Xinyu Lu et al.; arXiv preprint, v1 3 Jun 2026; [arXiv 2606.04455](https://arxiv.org/abs/2606.04455); abstract page read (curl)): meta-agents that iteratively program an agent for a held-out test set across five domains "rarely match human-engineered baseline policies", with high variance and "emergent adversarial behaviors like ground-truth exfiltration". Connection: supports held-out seeds, the worry that an LLM mutation step under selection pressure will look for the key and replicating evolution runs, not just evaluations.
- **Phantom Guardrails: When Self-Improving Agent Harnesses Fix Failures That Never Happened** (Su Wang et al.; arXiv preprint, v1 13 Jul 2026; [arXiv 2607.13083](https://arxiv.org/abs/2607.13083); abstract page read (curl)): on legal input with a harmless rule-like pattern a self-improving harness invented a failure "in 15/60 runs, versus 0/60 on featureless input", and inside an add-only accept loop it re-entered that state and stayed in it. Connection: a mutation proposer told the council missed bugs may add rules for failures that never happened, which the keep-only-if-CI-above-zero rule should block.
- **Optimization Instability in Autonomous Agentic Workflows for Clinical Symptom Detection** (Cameron Cagan et al.; arXiv preprint, v1 17 Feb 2026; [arXiv 2602.16037](https://arxiv.org/abs/2602.16037); abstract page read (curl)): validation sensitivity oscillated between 1.0 and 0.0 across iterations, and at 3% prevalence the system "achieved 95% accuracy while detecting zero positive cases", while a retrospective selector agent prevented catastrophic failure. Connection: with rare bugs an accuracy-like fitness rewards silence, so any combined council fitness should be checked for a "flag nothing" optimum.
- **Exploiting LLM-as-a-Judge Disposition on Free Text Legal QA via Prompt Optimization** (Mohamed Hesham Elganayni et al.; ICAIL 2026 per the arXiv comment; v1 22 Apr 2026, v2 23 Apr 2026; [arXiv 2604.20726](https://arxiv.org/abs/2604.20726); abstract page read (curl)): ProTeGi optimisation with feedback from two judges found "strict judges produce restrictive feedback, leading to judge-specific overfitting", while prompts tuned under a lenient judge transferred better. Connection: a council evolved under one judge may overfit that judge's disposition, which supports the cross-family judge arm and scoring against the planted key.
- **p1: Better Prompt Optimization with Fewer Prompts** (Zhaolin Gao et al.; arXiv preprint, v1 9 Apr 2026, v2 26 Aug 2026; [arXiv 2604.08801](https://arxiv.org/abs/2604.08801); abstract page read (curl)): "Prompt optimization succeeds when variance among system prompts is sufficiently large, but fails when variance among responses dominates", and selecting high-variance prompts beat baselines such as GEPA. Connection: the project should measure a council's rerun variance on the same seed before evolving, while keeping the held-out seeds unselected.
- **Anthropic hillclimb: Automating eval design and hillclimbing with Claude** (Lance Martin; claude.dev blog ("Playbooks"), 28 Sep 2026; Anthropic blog; https://claude.dev/blog/automating-eval-design-and-hillclimbing/; page read (curl, stripped to text; overfitting and hillclimb sections read in full)): Anthropic's recipe keeps a train set the hillclimber may read and a test set "that is never seen", keeps a patch only if both improve and leaves the code at the version "that did best on the test set", with an example reaching "90.5% against the original setup's 78.6%, at about one fifth of the cost". Connection: close to the project's keep-or-revert loop, but its test set is used for selection, so the project needs a final held-out set that no keep decision reads.
- **RoboPhD: Evolving Diverse Complex Agents Under Tight Evaluation Budgets** (Andrew Borthwick et al.; arXiv preprint, v1 6 Apr 2026; [arXiv 2604.04347](https://arxiv.org/abs/2604.04347); abstract page read (curl)): comparing Elo tournament selection, Pareto selection (GEPA) and greedy hill-climbing under "a fixed budget of 1,500 evaluations", the Elo method won on three of four benchmarks. Connection: an equal-budget comparison of selection rules the project could cite for its CI-gated rule, though its "validation-free" selection is exposed to the winner's curse.
- **TextReg: Mitigating Prompt Distributional Overfitting via Regularized Text-Space Optimization** (Lucheng Fu et al.; arXiv preprint, v1 20 May 2026, v2 5 Oct 2026; [arXiv 2605.21318](https://arxiv.org/abs/2605.21318); abstract page read (curl)): optimised prompts "often become longer, accumulate narrow sample-specific rules, and generalize poorly beyond the training distribution", and regularisation gave OOD gains "of up to +11.8% over TextGrad and +16.5% over REVOLVE". Connection: supports tracking brief length across generations and penalising growth in evolved reviewer briefs.
- **What Should the Reflector See? An Empirical Study of Evidence in Reflective Prompt Optimization** (Xiaofan Zhou and Lu Cheng; arXiv preprint, v1 26 Sep 2026; [arXiv 2609.32452](https://arxiv.org/abs/2609.32452); abstract page read (curl)): with Qwen3.5-9B as task model and reflector, "Failures-only produces the largest mean test gain (+8.0 percentage points)", and "calibration gains can overstate held-out improvement". Connection: what the mutation proposer is shown (missed seeds only or a mix) is a cheap ablation for the mutation step.
- **Textual Gradients are a Flawed Metaphor for Automatic Prompt Optimization** (Daniel Melcer et al.; arXiv preprint, v1 15 Dec 2025; [arXiv 2512.13598](https://arxiv.org/abs/2512.13598); abstract page read (curl)): finds that TextGrad-style methods often improve performance but "the gradient analogy does not accurately explain their behavior". Loosely related: a caution against reading feedback-driven brief mutations as principled descent.
- **Promptbreeder: Self-Referential Self-Improvement Via Prompt Evolution** (Chrisantha Fernando et al.; arXiv Sep 2023, Semantic Scholar venue ICML, edition not confirmed; [arXiv 2309.16797](https://arxiv.org/abs/2309.16797); abstract page read (curl)): evolves task prompts and, self-referentially, the mutation prompts, evaluating them "for fitness on a training set", with no held-out-noise analysis in the abstract. Connection: the original self-referential prompt evolver, a precedent for evolving the mutation step as well as the briefs.
- **TextGrad: Automatic "Differentiation" via Text** (Mert Yuksekgonul et al.; arXiv Jun 2024, Semantic Scholar venue arXiv.org only; [arXiv 2406.07496](https://arxiv.org/abs/2406.07496); abstract page read (curl)): "backpropagates textual feedback provided by LLMs", raising GPQA zero-shot "from 51% to 55%". Loosely related: a feedback-driven text optimiser, the kind of method the Textual Gradients paper cautions about.
- **DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines** (Omar Khattab et al.; arXiv Oct 2023; [arXiv 2310.03714](https://arxiv.org/abs/2310.03714); abstract page read (curl)): optimises pipeline demonstrations and prompts to "maximize a given metric". Loosely related: a general pipeline optimiser that could tune council briefs, with no review-specific result.
- **MIPRO: Optimizing Instructions and Demonstrations for Multi-Stage Language Model Programs** (Krista Opsahl-Ong et al.; EMNLP 2024 per the arXiv comment; [arXiv 2406.11695](https://arxiv.org/abs/2406.11695); abstract page read (curl)): uses "a stochastic mini-batch evaluation function for learning a surrogate model of our objective" and gains up to "13% accuracy" over baselines with Llama-3-8B. Connection: its mini-batch surrogate is an explicit treatment of noisy fitness, which bears on the project's selection rule.
- **GEPA** (authors not given; v2 14 Feb 2026, "Accepted to ICLR 2026 (Oral)" per the arXiv comment; [arXiv 2507.19457](https://arxiv.org/abs/2507.19457); abstract page read (curl)): listed as already among the IDs cited in the repo, with the new version and venue as the only new facts. Loosely related: a prompt optimiser used as a baseline by p1 and RoboPhD; it is not entered in prior-work-research.md.
- **Gödel Agent: A Self-Referential Agent Framework for Recursive Self-Improvement** (Xunjian Yin et al.; ACL 2025 main per the arXiv comment; v4 May 2025; [arXiv 2410.04444](https://arxiv.org/abs/2410.04444); abstract page read (curl)): listed with its citation only, with no summary. Loosely related: background on recursive self-improvement alongside the DGM line.
- **STOP: Self-Taught Optimizer: Recursively Self-Improving Code Generation** (Eric Zelikman et al.; COLM 2024 per the arXiv comment; [arXiv 2310.02304](https://arxiv.org/abs/2310.02304); abstract page read (curl)): a scaffold that improves itself and also measures "the frequency with which the generated code bypasses a sandbox". Connection: an early reward-hacking measurement, which bears on keeping the seed key out of reach of an evolving council.
- **SICA: A Self-Improving Coding Agent** (Maxime Robeyns et al.; v2 May 2025; [arXiv 2504.15228](https://arxiv.org/abs/2504.15228); abstract page read (curl)): a self-editing agent with "performance gains from 17% to 53% on a random subset of SWE Bench Verified". Loosely related: self-improvement for coding, not review, and one of the systems Trusting Trust Revisited poisoned.
- **ShinkaEvolve** (Robert Tjarko Lange et al.; arXiv Sep 2025; [arXiv 2509.19349](https://arxiv.org/abs/2509.19349); abstract page read (curl)): sample-efficient program evolution with "code novelty rejection-sampling" and "bandit-based LLM ensemble selection", with a circle-packing result "using only 150 samples". Loosely related: sample efficiency matters under the project's tight seed and token budgets.
